# 工具定义

> 模型可用的全部工具与每个工具的代码层约束。判据、时机、风格一律不在这里——那些归提示词（ADR-0014）。工具只做三件事：验证输入、落库、拒绝非法操作。
>
> 相关决策：ADR-0005（只提议不写死）、ADR-0014（分工）、ADR-0017（去重）、ADR-0019（四档直出）、ADR-0021（节奏归模型）、ADR-0026（学习对话取卡标反模式）。

## 设计总纲

1. **工具面越小越好。** 模型对卡片和术语都没有物理增删权，只有状态提案权（ADR-0005）。改卡不设工具——AI 在对话里发现卡面有误，让用户去 WebUI 改，或删卡重制。
2. **判据不进工具。** 什么时候制卡、一批取几张、答成什么样判哪档——模型的事，工具不做评分、不给建议、不限制节奏。
3. **返回值给模型判断的原料，不给结论。** 制卡工具拒绝精确重复时附上该 Topic 现有 `front` 列表，模型自己判断是放弃、改角度还是提议合并（ADR-0017）——工具说「重了」就完了，判断留给模型。
4. **时间戳由代码填。** 所有 `created_at` 等时间字段由代码取当前时间写入（schema 的 `DEFAULT (datetime('now'))`），模型不传、也不需要传——模型口中的「今天」不可信。

## 可见性矩阵

**实现载体**：以下工具全部由 pi-teacher 的 **Pi 插件（extension）**实现——`extensionFactories` 工厂内 `pi.registerTool(defineTool({...}))`，注册在后端宿主进程内（ADR-0024；customTools 参数路线已否决，走扩展工厂便于后续拆装与事件挂钩）。外部能力扩展只有 skill 和插件两个载体，不用 MCP（ADR-0027）。文件类工具（md 导航、文件探查）是插件内的 Node 函数，不是独立 CLI。

**命名约定（定稿）**：工具名用前缀分组——`card_*`（制卡增删查改）、`topic_*`、`glossary_*`（术语增删查改）、`review_*`（取卡与判定）、`md_*` / `file_*`（文档导航与文件探查）。前缀是给模型的命名簇，也是代码的文件边界（一文件一组）。工具名不得含点号——Anthropic API 工具名仅允许 `^[a-zA-Z0-9_-]{1,128}$`，下划线安全。

## card_propose 制卡

学习或复习对话中提议一张卡。**固定写 `status = 'proposed'`**，进待审批列表，用户确认前不影响任何复习行为。

```
card_propose(topic_name, front, back, reason_and_remark, source_essence_path?)
```

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `topic_name` | string | 传名称不传 id。按 `topic.name` 精确匹配现有 Topic |
| `front` | string | 正面（问题） |
| `back` | string | 背面（参考答案或评价标准） |
| `reason_and_remark` | string | 为什么造这张卡、补充说明 |
| `source_essence_path` | string? | 出自哪个 essence 文件，绝对路径 |

代码层硬约束：

- **Topic 必须已存在。** 匹配不到时拒绝，返回值提示模型「先 `topic_list` 核对，确为新主题再 `topic_create`」——建 Topic 是一个显式动作，不藏在制卡流程里隐式发生。
- **精确去重（ADR-0017）**：同 Topic 下 `front` 归一化后已存在则拒绝。归一化 = 去首尾空白 + 压缩连续空白 + 统一中英文标点 + 忽略大小写。去重范围按 Topic 不按工作区。
- 制卡开关关闭时拒绝，返回值里说明「本次对话已关闭制卡」。

返回值两种形态：

- **成功**：`{ created: true, card_id }`，附该 Topic 现有卡片的 `front` 列表（按创建时间倒序，最多几十条）——给模型事后察觉语义相似的机会。
- **拒绝**：`{ created: false, reason: 'duplicate' | 'topic_not_found' | 'make_card_disabled', ... }`——重复时附完整 `front` 列表，Topic 不存在时附提示，让模型自己决定下一步。

## topic_create

```
topic_create(name, description?)
```

新建一个 Topic，FSRS 参数用默认值（`request_retention = 0.9`、`maximum_interval = 365`），用户之后可在 WebUI 的 Topic 管理页调。`name` 全局唯一（`UNIQUE` 约束），重名拒绝。

**不需要用户审批**：Topic 是组织工具不是学习内容——卡片才审内容，Topic 建错了改名即可，让审批流等在这里只会拖慢制卡。与 `card_propose` 同可见性：制卡开关控制，助教硬拒。

## card_list 与 card_get 卡片查询

查询拆成两层，与术语查询同构：**列表轻、详情重**。

```
card_list(topic_id?)
card_get(card_id)
```

**`card_list`** —— 列出卡片，每条只返回 `id`、`topic_name`、`front` 的结构化 JSON。`topic_id` 可选，用于「这个 Topic 下已有哪些卡」这类核对（去重判断、合并判断前先扫一眼）。只列 `status = 'normal'` 的卡——`proposed` 是审批流程的中间态、`deleted` 是回收站，两者模型要么刚写入过（上下文里有记录）要么不该看见；用户审批与回收站是 WebUI 的领域。

**`card_get`** —— 返回某张卡的全部字段（`SELECT * WHERE id = ?` 级别的完整信息）：`id`、`topic_id`、`topic_name`、`front`、`back`、`status`、`reason_and_remark`、`source_essence_path`、`created_at`。

## card_delete 软删

```
card_delete(card_id, reason?)
```

固定写 `status = 'deleted'`，进回收站。**不需要用户确认**——软删除可恢复、`review_log` 不级联保留（数据无损），不构成越权（ADR-0005 管的是写入门槛）。`reason` 追加到 `reason_and_remark` 末尾，回收站里显示给用户看。物理删除只发生在用户手动清空回收站。

## card_merge 合并

AI 判定几张卡高度重复、用户在对话中同意后执行。**合并动作归工具，AI 不碰 FSRS 状态计算**（`todo.md` 已定）。

```
card_merge(target_front, target_back, merged_card_ids, reason_and_remark)
```

工具原子完成三件事：新卡入库（`status = 'normal'`，直接进复习队列）、被合并的旧卡全部置 `deleted`、新卡的 `card_schedule` 初始状态从旧卡推导。**推导算法已定：复制 `stability` 最低那张旧卡的调度状态**——记忆估计宁低勿高，宁可让新卡早点再到期，也不要凭空高估用户的记忆强度；顺带避免「按 `Good` 重新走一次调度」会凭空产生一条没发生过的 `review_log`、污染 FSRS 优化样本的问题。合并出的卡不再走用户审批——它替换的是已确认的卡，再审批一轮意味着旧卡在等待期继续留在队列里，违背合并的初衷；用户在对话中的明确同意就是确认（ADR-0005 的门槛不降低，只是确认发生在对话里）。

## glossary_propose 术语提议

提议一个「用户已彻底掌握」的术语。**固定写 `status = 'proposed'`**，用户确认前查询工具不可见。

```
glossary_propose(term, definition)
```

- `term` 全局唯一（`UNIQUE` 约束），已存在则拒绝并返回现有那条的 `definition`——模型核对后要么放弃，要么判断现有那条质量不行，让用户在 WebUI 处理。
- `definition` 应取工作区 `GLOSSARY.md` 里用户自己的话，不重写（ADR-0020，提示词约束，工具不校验内容只校验唯一性）。

## glossary_list 与 glossary_get 术语查询

查询拆成两层，与卡片查询同构：**列表轻、详情重**。只返回 `status = 'normal'` 的术语（未确认的记录不能影响讲解行为，ADR-0005）。

```
glossary_list()
glossary_get(term_id)
```

**`glossary_list`** —— 无参，返回 `[{ id, term }]` 的结构化 JSON。这是全局用户模型的目录页——`USER.md` 里的引导句说「`glossary` 表中记录了用户当前已掌握的术语，可通过数据库工具读取，用这些信息优化教学方法」，何时读、读来干什么由模型自主判断。

**`glossary_get`** —— 传 `id`，返回该条全部信息（`id`、`term`、`definition`、`created_at`）。

两层拆开的理由：扫一眼术语名很便宜（每条两三个 token），模型先拿目录判断哪些相关，再按 id 取那几条的完整定义——避免每次查询都把全量 `definition` 拉进上下文。

## topic_list

返回全部 Topic：`id`、`name`、`description`、卡片数、到期数。制卡时模型先看这个列表优先复用，避免同义词泛滥（`数据库设计.md`）。

## review_get_due_cards 取卡

```
review_get_due_cards(nums, topic_id?)
```

只暴露 `nums`——取多少张由模型结合用户偏好与能力自主决定，代码不设默认节奏（ADR-0021）。挑选逻辑仅一条：`status = 'normal'` 且 `due` 已到，按 `due` 升序（最逾期的在前）。`topic_id` 来自 `pi_session.review_topic_id`，null = 不过滤。学习对话里这是反模式（ADR-0026）：工具不拦，提示词管。

`nums` 有防御性上限 **100**——一次取上千张会爆上下文，超出截断并在返回值注明还有多少张没取到。上限只约束单次调用，不约束总量：批次判定落库后 FSRS 重算 `due`，队列消化掉一批，再取下一批。积压靠「取卡 → 复习 → 判定 → 再取」的循环处理，不靠一次取完。

返回每张卡：`id`、`front`、`back`、`reason_and_remark`、`source_essence_path`、`topic_name`、`last_review`、`reps`、`lapses`——复习历史让模型自己制定出题策略（失误多的卡多追问一步），这是「判断归模型」的又一次应用。

## review_submit_ratings 判定

```
review_submit_ratings([(card_id, rating)])
```

批量提交（ADR-0018），`rating` 直接四档 `Again / Hard / Good / Easy`，无中间映射层（ADR-0019）。代码只做枚举校验，档位含义在复习提示词的 rubric 里。

落库时工具写 `review_log` 并用 FSRS 更新 `card_schedule`，模型不感知调度细节。（曾设计过「只接受本会话取过的卡」的防串卡限制，用户裁决不加。）

WebUI 直接刷卡（不经 AI 的第二条路径，ADR-0021）走后端同一个落库函数，但那是 REST 接口不是模型工具。

## md_get_outline 与 md_get_section 长文档导航

`materials/` 里的课程转录动辄几万字，全文 `read` 会占爆上下文；`grep` 拿得到标题行，但「某标题下到哪里为止」要算同级边界，把边界计算交给模型是算术负担且易错。两个工具补上这一环，与 `glossary` 同一个模式：**程序让模型知道有什么、怎么取，不替它决定取什么。**

```
md_get_outline(path, level?)
md_get_section(path, heading)
```

**`md_get_outline`** —— 返回 Markdown 标题目录，每行带行号与层级标记：

```
12: ## 梯度下降
42: ### 数学定义
87: ### 收敛性
```

`level` 可选（1–6），不给返回全部级别——「获取所有 3 级标题」就是 `level = 3`。行号是给模型下一步用的：Pi 自带 `read` 支持 `offset` / `limit`，模型看到行号就能精确读任意段，这两个工具与 `read` 是组合关系不是替代。

**`md_get_section`** —— 取某个标题下的**全部内容**（含子标题及其内容），边界由工具算：从该标题行起，到下一个**同级或更高级**标题为止。`heading` 按文本匹配，不带 `#` 前缀也能命中；超长文档里重名子标题（如多个「总结」）不算罕见，命中多处时全部返回、每段带起止行号。

两个都是只读工具。实现是扩展内的 Node 函数（ADR-0006 的载体原则：业务逻辑进扩展），不是独立 CLI——不涉及「Shell / Node / Go 三条路」的分工。

## file_get_size_and_length 文件探查

```
file_get_size_and_length(path)
```

读长文件前的第一步：先探大小，再决定策略——直接 `read`、先 `md_get_outline` 再分段、还是让资料抓取子代理去摘要。

返回：

```json
{ "characters": 48213, "lines": 1204, "bytes": 151020 }
```

`lines` 与 `bytes` 都给，是因为 Pi 自带 `read` 的截断规则是「行数或字节数先到为准」——模型拿着这两个数就能预判会不会被截断，该用 `offset` / `limit` 分几段读心里有数。只读工具。

## 不做成工具的东西

| 能力 | 归属 | 出处 |
| --- | --- | --- |
| 改卡（编辑 front / back） | WebUI 用户操作，AI 无此工具 | 最小工具面推导 |
| 提醒注入（到期提醒、偏好提醒） | 后端 hook 拼 `<system-reminder>` 进 `context` 事件 | open-questions 已决 |
| 助教的「当前学习上下文」 | 后端读工作区 AGENTS.md 拼注入，非工具 | `数据库设计.md` |
| 对话标题生成 | 后端独立 LLM 调用，不进会话上下文 | `数据库设计.md` |
| 消息回退 / 重新生成 / 编辑重发 | 用户操作，后端直接调 `session.navigateTree()`，与模型工具面无关 | `pi-会话生命周期调研.md` Q5 |
| 生图 | skill 实现（含下载落盘，返回本地路径） | ADR-0023、ADR-0027 |
| 资料抓取 | 子代理自有工具面，业务工具对子代理隐藏 | ADR-0016 |
| 写文件（essence、GLOSSARY.md、learning-records） | Pi 自带文件工具，不重复造 | — |
