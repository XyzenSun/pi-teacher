# 已确认的架构与产品决策

> 本文只记录截至 2026-09-03 已经在讨论中明确确认的内容。没有明确决定的事项放在文末的“未决问题”，不把建议误写成结论。

## 1. 产品目标

Pi Teacher 是一个基于 Agent 的 Web 学习助手。核心价值是通过不同学习风格帮助用户理解、练习和长期保持知识，而不是做一个单纯的背词或卡片翻译工具。

项目首版虽然需要一个可运行的产品，但重点不是只实现面试八股文，而是先把系统架构做得尽可能模块化、插件化，以便支持不同学习领域和学习方式。

编程学习只是一个典型示例，未来还要支持非编程领域，例如背单词、其他知识主题以及依赖视觉辅助的学习场景。

## 2. 产品形态与用户范围

- 交互入口是 Web UI，不做终端对话。
- 当前定位是纯自用单用户。
- 暂不以公开 SaaS、多租户、计费和大规模用户隔离为首要目标。
- 设计时可以为未来扩展预留合理的标识，但不为尚不存在的多租户需求提前堆叠基础设施。

## 3. Agent 底座

### 3.1 已选方案

Agent 底座确定使用 Pi Agent Harness，即 `earendil-works/pi`。

不再继续研究或比较 DeepSeek Harness。

Pi 的定位是 Agent Loop 的执行器，项目不自行实现以下底层能力：

- Agent Loop
- 流式对话
- tool calling 解析
- tool 调用执行循环
- 自动上下文压缩

系统必须保留并利用 Pi 的自动上下文压缩能力，因为即使是很短的对话，也可能达到模型上下文上限。

### 3.2 技术栈

由于 Pi 的 SDK 以 TypeScript 为主，项目采用全栈 TypeScript，避免通过独立进程或 IPC 为 Pi 增加额外语言边界。

## 4. 学习空间与学习类型

### 4.1 workspace

一个 workspace 是一个长期存在的学习主题容器，可以包含：

- 整体学习目标和任务背景
- 用户提供的资料
- 多次学习会话
- 学习过程中的笔记和难题
- 卡片及其复习状态（长期 workspace）
- 用户偏好和学习表现相关的上下文

一个 workspace 下可以有多场独立对话。

### 4.2 type 挂在 workspace

学习类型确定挂在 workspace 上，而不是每一场 session 上：

- `short-term`：短期学习，不进入长期复习计划，不制卡。
- `long-term`：长期需要复习的学习，才维护卡片、复习状态和复习提醒。

长期 workspace 中，用户可以临时询问与整体学习目标无关的问题。这类问题不会改变 workspace 的长期目标；通过提示词约束，模型不应为无关闲聊制卡。

目前没有必要支持从长期 workspace 降级为短期 workspace。

### 4.3 短期升长期

短期学习可以升级为长期学习。

升级时：

1. 用户选择一次短期学习会话或该会话凝结出的学习结果。
2. 系统新建一个长期 workspace，或让用户选择已有的长期 workspace。
3. 将短期会话中的凝结结果导入目标 workspace。凝结结果包括用户笔记、遇到的难题、重要结论等，而不是强制让模型重新阅读整段原始对话。
4. 自动执行一次制卡流程，由 AI 根据导入的学习结果提议卡片。
5. 卡片是否正式入库仍遵循卡片确认规则（具体确认交互尚未最终确定）。

短期会话本身也应支持压缩和凝结，以便形成可迁移的结构化学习结果。

## 5. session 与 workspace 的关系

- `workspace` 是业务层的持久化学习主题。
- `session` 是一整场 Pi 对话，可能包含几十轮用户与 AI 的来回消息，不是一条消息对应一个 session。
- 一个 workspace 可以包含多个 session。
- 学习 session、复习 session 可以分别创建，避免不同学习风格和任务混在一条上下文里。
- 默认采用“一场对话 = 一个 Pi session”的关系。
- 跨 session 的连续性通过 workspace 中持久化的资料、摘要、卡片、学习记录和 briefing 重建，而不是依赖一条无限增长的长上下文。

### 5.1 历史可见性

即使使用独立 session，用户也必须能在 Web UI 中查看历史对话。

Pi 的自动上下文压缩只改变发送给模型的运行时上下文，不应隐藏或删除 Web UI 展示的完整历史。Pi 的 append-only 会话存储会保留压缩前的消息。

### 5.2 session 标题

历史对话需要有可见标题：

- 支持 Pi 自动生成会话标题，或者通过 Pi API / 扩展写入标题。
- Web UI 提供修改会话标题的能力。
- 标题属于会话展示元数据，不应依赖模型每次重新生成。

## 6. 记忆与确定性数据

### 6.1 记忆分层

系统至少区分：

- 用户偏好：例如表达偏好、类比禁忌、代码示例偏好。
- workspace 工作记忆：当前学习目标、资料、笔记、难题、已知薄弱点和学习进度。
- 会话历史：由 Pi 持久化，支持历史查看和后续恢复。
- 复习计划与卡片状态：长期 workspace 的确定性业务数据。

### 6.2 数据职责

Pi 负责 Agent 会话和 Agent Loop 相关状态；业务侧必须保存确定性数据。

即使 Pi 能保存会话，也不能把所有业务状态交给模型上下文或自然语言。复习日期、卡片状态、用户确认结果等必须能被稳定读取、更新和审计。

应用数据库的具体选型尚未最终确定。当前方向是使用轻量数据库保存业务数据；单用户部署优先考虑 SQLite，而不是为了会话存储再重复建设一套数据库。

Pi 会话存储与业务数据库通过 `sessionId`、`workspaceId` 等标识关联。

### 6.3 上下文压缩与业务状态

Pi 的自动压缩保留给 Agent 使用。压缩可能改变模型可见的消息上下文，因此：

- 不能把不可丢失的业务事实只放在普通消息中。
- workspace briefing、卡片状态、学习记录和用户偏好应由后端从持久化数据生成。
- briefing 可以在每轮请求前重新组装或注入，使模型获得最新状态。
- 完整会话历史仍由 Pi 存储并供 Web UI 查看。

## 7. 复习与卡片

### 7.1 长期学习才制卡

普通短期学习不制卡。

只有 `workspace.type = long-term` 时，模型才需要被提醒考虑维护卡片。长期 workspace 中不是每个话题都必须制卡；与学习目标无关的临时问题也不应自动制造卡片。

面试八股文、算法题等都可以统一包装成卡片：

- 卡片正面是问题或任务。
- 卡片背面是参考答案、解题方向或评价标准。
- AI 负责结合用户自己的理解进行追问、解读回答、指出错误和给出建议。
- 算法题的卡片可以要求用户重新解释或重新完成题目，具体代码执行能力作为后续可扩展能力。

背单词等有固定答案的场景不是当前差异化重点，但系统架构不能排除它；例如 Apple 可以使用苹果图片作为视觉记忆辅助。

### 7.2 调度算法

复习日期不由 AI 自由拍脑袋决定。采用 FSRS 作为调度基线，优先复用 `ts-fsrs`，而不是嵌入完整 Anki 应用或通过 AnkiConnect 依赖本地 Anki 进程。

确定的分工是：

- AI：评价开放式回答的正确性、完整性、理解深度和回答难度，并提出解释与建议。
- 代码/FSRS：根据结构化 rating 计算下一次 due date 和卡片状态。
- AI 可以在业务规则允许的情况下提出特殊调度建议或覆写请求，但覆写不是首版默认路径，必须经过明确工具和业务校验。

FSRS 的 `Again / Hard / Good / Easy` 不是简单的 0-100 分线性映射：

- 回答错误或核心结论错误：应判为 `Again`。
- 回答正确但明显吃力：可判为 `Hard`。
- 回答正确且掌握稳定：根据表现判为 `Good` 或 `Easy`。

AI 的评价结果需要结构化落库，再由 FSRS 计算卡片状态。复习记录应保留，以便未来分析和训练个性化参数。

### 7.3 卡片提议与确认

已确定方向是 AI 提议卡片，而不是无条件自动制造卡片。具体的提议确认 UI 仍需继续讨论。

已确认约束：

- 长期 workspace 才触发维护卡片的提醒。
- AI 可以在对话中发现值得长期记忆的知识点并提议卡片。
- 需要避免长对话中的卡片洪水。
- 确定性写入应使用结构化 Pi tool，而不是解析自然语言。

## 8. Hook 与周期提醒

### 8.1 只对模型注入隐式提醒

Hook 的提醒对象是 AI，不是用户。用户界面不应因为周期提醒频繁弹窗或打断学习。

提醒内容不需要在正常回复中向用户汇报；只有确实产生了卡片、偏好等变更时，才展示相应结果。

### 8.2 长期学习提醒

当 workspace 类型是 `long-term` 时，Hook 才触发卡片维护提醒。普通学习（`short-term`）不制卡，也不注入制卡提醒。

卡片提醒的轮次阈值是可配置的，例如每隔一段轮次注入一次；具体默认值还未最终确定。Hook 应动态检查当前状态，不应在已经没有新增内容时无休止催促。

提醒的意图是让模型考虑是否需要维护卡片，而不是强迫模型每次都创建卡片。

### 8.3 用户偏好提醒

用户偏好以手写为主，AI 只负责提议：

- 用户可以直接在 Web UI 编辑偏好。
- AI 发现稳定、可复用的用户偏好时，可以调用 `propose_preference` 提议。
- 提议需要用户确认后才生效。
- Hook 周期性提醒模型考虑是否有必要更新用户偏好。
- 偏好提醒比卡片提醒慢，倾向于每 30 轮触发一次。
- 如果没有值得更新的偏好，模型不需要在回复中提及这次检查。

### 8.4 提醒合并

如果偏好提醒与长期 workspace 的卡片提醒在同一时机触发，应合并为一条内部提醒，让 AI 自己判断是否需要处理，而不是分别注入多条提醒。

## 9. 扩展载体

项目不把所有扩展能力粗暴地归类为同一种“插件”。根据 Pi 的能力边界，允许组合使用：

- Pi Skill：用 Markdown 描述学习方法、教学风格、制卡规范、评分 rubric 和其他模型行为约束。
- MCP：如果未来需要跨 Agent 底座复用的外部能力，可以考虑 MCP；但 Pi 核心目前没有官方内置 MCP 支持，需要额外适配或社区方案。
- Pi Extension：需要访问 Pi 生命周期、Agent Loop、上下文、事件、Hook、运行时权限或高权限资源时，写成 Pi Extension。
- 普通业务模块：数据库访问、FSRS 调度、workspace 服务、复习队列等确定性逻辑仍属于应用代码，不因为“可扩展”就全部动态插件化。

最终采用哪一种载体，应根据能力需求决定：

- 只需要模型知道“怎么做”时，优先 Skill。
- 需要主动介入 Agent Loop、按轮次注入提醒、监听会话生命周期时，使用 Pi Extension。
- 需要执行确定性业务操作时，使用结构化 tool 调用到应用服务。
- 需要调用外部服务时，可以由 Pi Extension 封装，或在确定需要跨 harness 复用时再引入 MCP。

Pi Extension 在 Node 进程内运行，具有较高权限且没有内置沙箱。因此只加载受信任的扩展；生图、数据库、网络访问等能力必须由业务侧控制权限、参数和成本。

## 10. 内容格式与视觉能力

### 10.1 默认 Markdown

首版默认使用 Markdown 作为学习内容和课件输出格式，原因是：

- 生成成本较低。
- Token 消耗比直接生成完整 HTML 更少。
- 适合流式输出和 Web UI 展示。
- 便于保存、检索、编辑和版本化。

### 10.2 可选 HTML

HTML 作为可选输出能力，后续再实现服务端渲染。需要明确向用户说明：完整 HTML 会增加模型输出量和 Token 成本，也会增加渲染与安全处理成本。

### 10.3 Mermaid

Mermaid 可作为 Markdown 中的结构化图表能力，用于流程图、时序图、状态图和其他关系清晰的内容。它不能覆盖所有视觉需求。

### 10.4 AI 生图

AI 生图是必要的可选能力，不仅面向编程学习。适合具象对象和视觉记忆辅助，例如背单词时为 `Apple` 生成苹果图片；也可以用于某些教学风格的简单视觉辅助。

首版优先做好“Markdown + AI 生图”组合：

- Markdown 默认开启。
- 生图默认作为可选项，可由用户或模型根据场景决定是否生成。
- 生图服务的费用、等待时间和失败处理需要在产品中明确。
- Mermaid 与 AI 生图不是互相替代的方案，二者可以并存。

对于严格的结构化技术图，优先使用 Mermaid 或其他可验证的图表 DSL；AI 生图用于视觉记忆锚点和无法用图表 DSL 表达的具象内容。

## 11. Web UI 与 Pi 集成方向

- Pi 作为 Node/TypeScript 后端中的库运行，不启动终端对话。
- 由 Pi 提供 Agent Loop、tool calling、事件流和自动上下文压缩。
- 后端把 Pi 事件转换为浏览器需要的 SSE 或 WebSocket 消息。
- Web UI 自己实现会话列表、历史消息、标题编辑、workspace、卡片和复习界面。
- Pi 核心没有可直接复用的官方交互式 Web UI，因此前端仍需自行开发。

## 12. 当前明确不做或暂缓

- 不再研究 DeepSeek Harness 作为底座。
- 不自己重写 Pi 已提供的 Agent Loop、流式对话、tool calling 和上下文压缩。
- 不把短期学习自动加入长期复习计划。
- 不支持长期 workspace 降级为短期 workspace。
- 不把 AI 作为复习日期的唯一决定者。
- 不把所有能力都强行实现为动态插件。
- 不把 HTML 作为首版默认输出。
- 不把 AI 生图强制用于每个知识点。
- 不把面向固定答案的背单词作为唯一或首版唯一场景。

## 13. 未决问题

以下事项在当前对话中尚未最终决定：

1. Pi 的具体版本、依赖安装方式和服务端嵌入 API 的最终封装。
2. Web 后端框架与前端框架。
3. 应用数据库具体 schema，以及 SQLite 是否最终作为首选实现。
4. Pi 会话存储采用默认 JSONL，还是采用 Pi 官方 SQLite session backend。
5. workspace / session / Pi session metadata 的最终映射字段。
6. 卡片提议的具体确认交互，以及一场学习会话的卡片数量上限。
7. 卡片、学习摘要、难题记录由哪些 Pi tools 写入，哪些由 Hook 监听后生成。
8. FSRS rating 的具体 AI 评价 rubric 与 0-100 评价到四档 rating 的映射规则。
9. 是否启用 FSRS 个性化参数训练，以及最少需要积累多少有效复习记录。
10. 到期队列的分组、每日上限、积压处理和特殊日期处理。
11. 卡片复习是逐卡问答、topic 分组对话，还是同时提供两种模式。
12. Pi 自动标题生成使用什么模型、何时触发，以及标题生成失败时的回退规则。
13. Hook 的默认卡片提醒轮次；用户偏好提醒暂定为 30 轮。
14. AI 生图服务、模型、图片存储方式、预算限制和重试策略。
15. Mermaid 在 Web UI 中的渲染、安全过滤和失败回退。
16. HTML 输出能力的服务端渲染方案与上线时机。
17. 是否引入 MCP，以及首个需要跨 harness 复用的外部能力是什么。
18. 用户是否需要导出 workspace、学习资料、卡片和学习记录。
