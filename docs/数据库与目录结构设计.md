# 数据库与目录结构设计

> 当前 Schema 的完整快照，实现以本文为准。
> 需求来源见 `docs/学习区设计.md`。
> 相关决策：ADR-0010（职责边界）、ADR-0011（Topic 粒度）、ADR-0017（去重）、ADR-0020（术语入库）。

## 数据库的职责

**给前端提供渲染所需的读取性能，做卡片管理，存跨工作区的用户模型。**

前两件是主要职责。第三件只有 `glossary` 一张表——它进库是因为跨工作区共享，散在各工作区的文件里无法汇总。

| 类型 | 去处 | 例子 |
| --- | --- | --- |
| 前端要渲染或编辑的 | 数据库 | 工作区列表、对话列表、卡片、提示词模板 |
| 卡片与调度 | 数据库 | card、card_schedule、review_log |
| 模型读写的散文 | 文件系统 | 当前 Pi Session `work_path` 下的 MISSION.md、GLOSSARY.md、pi-session-user.md、learning-records/ |
| 用户直接看的成品 | 文件系统 | 当前 Pi Session `work_path` 下的 essence/、assets/ |
| 全局用户模型 | 数据库 | glossary（已掌握的术语） |

会话选用的提示词模板与教学风格存库，分别投影为该 Pi Session 的 `AGENTS.md` 与 `style.md`；全局 `~/pi-teacher/AGENTS.md` 不存库，由用户编辑文件，初始化只在缺失时写入出厂内容。

## 存储边界

| 存储 | 内容 | 格式 |
| --- | --- | --- |
| Pi 会话文件 | 对话历史、工具调用、压缩产物 | JSONL，位于每个 Pi Session 自己的 `work_path` |
| 业务数据库 | 本文所有表 | 单个 SQLite 文件 |
| 用户环境变量 | skill 需要的 `TAVILY_*` 等变量与值，含用户自加项 | 同一 SQLite 文件里的 `user_env` 表（ADR-0034），明文存储、明文回显，启动与保存时注入后端 `process.env`；没有 `.env` 文件 |
| 业务运行设置 | 维护提醒共用间隔 `reminder_interval_turns` 与四段文案 `reminder_text_*`（三段基础 + 学习精华追加段） | 同一 SQLite 文件里的 `setting` 表（ADR-0036 / ADR-0039），键值都是文本；缺行取代码默认值，不 seed。与 Pi 的 `settings.json` 无关 |

分库不合库：迁移历史各自演进（Pi 的会话 schema 尚未稳定，曾有不带迁移的破坏性变更）、写锁互不干扰、会话可单独归档而不动业务数据。两者之间没有需要原子保护的不变量。

选 SQLite，单用户部署（见 ADR-0015）。

## 两层容器与对话模型

系统只保留一个收纳层：

- **space** — 数据库中的收纳容器，聚类若干次 Pi Session，并用 `type` 区分 `learn` / `review` / `ta`；不拥有 Pi 工作目录
- **pi_session** — 一次 Pi 对话，归属于一个 Space，拥有独立的 `work_path` 与 JSONL 文件

Space 是纯数据库收纳箱，不提供跨 Pi Session 的文件上下文。同一个学习 Space 可以收纳学习 Java、数据库、Redis 的不同 Pi Session，但这些对话各自拥有独立的 `AGENTS.md`、`style.md`、JSONL 与本地产出。

**提示词挂在 pi_session 上**：每次开对话时选择 Agents Md、Teach Style 与制卡开关，投影只写入本次 Pi Session 的 `work_path`。

## 表关系

```
space ──< pi_session
              │
              ├──> agents_md      提示词模板
              ├──> teach_style    教学风格
              └──> topic          review_topic_id，仅复习对话有值

topic ──< card ──1:1── card_schedule    仅 status='normal' 的卡有调度行
                 └──< review_log       软删除不级联，记录保留供 FSRS 优化

glossary                                孤立表，无外键。全局用户模型
user_env                                孤立表，无外键。用户环境变量（ADR-0034）
setting                                 孤立表，无外键。业务运行设置（ADR-0036）
```

共 11 张业务表（另有认证用 `user` 表）：

| 表 | 作用 |
| --- | --- |
| `space` | Pi Session 的收纳容器与活动类型 |
| `pi_session` | 一次 Pi 对话，挂提示词、风格与独立工作目录 |
| `agents_md` | AGENTS.md 提示词模板库，含 `type` 区分适用 Space 类型 |
| `teach_style` | 教学风格库 |
| `topic` | 主题，卡片归类维度 + FSRS 参数配置粒度 |
| `card` | 卡片内容，含 `status` 三态（候选 / 正常 / 软删除） |
| `card_schedule` | FSRS 调度状态，与 card 一对一 |
| `review_log` | 复习记录，用于优化 FSRS 参数 |
| `glossary` | 用户已彻底掌握的术语，跨 Space 的全局用户模型 |
| `user_env` | 用户环境变量：`key` 主键、`value` 明文；内置 `TAVILY_*` 三项未设置时不占行 |
| `setting` | 业务运行设置：`key` 主键、`value` 文本。`reminder_interval_turns`（共用间隔，0 关闭全部提醒，缺行即默认 30）；`reminder_text_make_card_on` / `reminder_text_make_card_off` / `reminder_text_ta`（三段基础文案）与 `reminder_text_learning_essence`（仅学习同轮追加的精华段）。文案缺行即 `prompts/defaults.ts` 出厂值，PATCH 空串或纯空白删行恢复默认，不覆盖其余文案（ADR-0039） |

## space

`space` 是唯一的收纳容器表，不再另设 `session` 表。固定 Space 的 ID 只用于稳定外键与初始化，业务代码必须读取 `type` 判断活动类型。

```sql
CREATE TABLE space (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  type       TEXT NOT NULL,
  name       TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (type IN ('learn', 'review', 'ta'))
);

CREATE UNIQUE INDEX space_singleton_type
  ON space(type)
  WHERE type IN ('review', 'ta');
```

`ta` 与 `review` 的固定 Space 名称、类型和身份不可由 WebUI 修改或删除；只有 `learn` Space 可重命名或删除。

初始化写入两行固定容器：

| id | type | name | 语义 |
| --- | --- | --- | --- |
| 0 | `ta` | 助教 | 全局唯一助教容器 |
| 1 | `review` | 复习 | 全局唯一复习容器 |
| >= 2 | `learn` | 用户命名 | 用户创建的学习容器 |

`space.type` 与 `agents_md.type` 取值相同，但**不建立二者的外键**：前者表示容器的活动类型，后者表示模板的适用范围，是两个不同概念。创建 Pi Session 时由后端校验模板类型与 Space 类型匹配。

## agents_md

AGENTS.md 提示词模板库。用户在 WebUI 里切换，切换即覆盖文件。

```sql
CREATE TABLE agents_md (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  type        TEXT NOT NULL,  -- 'learn' | 'review' | 'ta'
  name        TEXT NOT NULL,
  description TEXT,           -- 给用户看的简介
  prompt      TEXT NOT NULL,  -- AGENTS.md 的正文

  CHECK (type IN ('learn', 'review', 'ta'))
);
```

预置模板（出厂内容统一收在 `server/src/prompts/defaults.ts` 的 `AGENTS_MD_TEMPLATES`，`seed.ts` 只在表里没有对应类型时插入；持续维护就改这一个文件）：

| `type` | 用途 | 说明 |
| --- | --- | --- |
| `learn` | 新学 | 默认学习模式，含制卡引导 |
| `learn` | 新学不制卡 | 纯讲解，不提议卡片 |
| `review` | 复习 | 出题、判定、给反馈 |
| `ta` | 助教 | 只答疑，不推进课程。`id = 0`，全局唯一 |

单独建表而不是把正文存在 pi_session 里：模板要跨对话复用，存正文会导致每次开对话都复制一份全文，改模板还得批量更新历史行。

### type 字段：给 WebUI 做候选过滤

新开对话时用户**先选会话类型，再选模板**。类型定了，模板列表就按 `WHERE type = 'learn'` 或 `WHERE type = 'review'` 筛出来。没有这个字段，用户会在复习会话里看到「新学不制卡」这种选项。

`type` 用字符串而非外键指向 `space`：这里要的是「这个模板能用在哪类会话」，与 `space` 表那个「会话属于哪类」是两回事，虽然取值恰好对应。用外键会让人以为改 `space` 就能影响模板分类。

**助教类型不出现在选择界面**。`ta` 模板只有 `id = 0` 一行，开助教对话时程序直接取它，不给用户选。它单独占一个 `type` 值只是为了不被 `learn` / `review` 的筛选误捞出来。

用户自建模板时必须指定 `type`，界面上就是「这个模板用于学习还是复习」。

## teach_style

教学风格库，与 agents_md 正交——前者定「做什么」，后者定「怎么说话」。

```sql
CREATE TABLE teach_style (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT NOT NULL,
  description TEXT,
  prompt      TEXT NOT NULL
);
```

预置若干行（循序渐进的老师、苏格拉底式追问等），用户可自定义。用表而不用 Skill 文件，因为用户要在界面上增删改（见 ADR-0006 修订）。

## pi_session

一次 Pi 对话。一行对应一个独立工作目录与其中的 JSONL 文件。

```sql
CREATE TABLE pi_session (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  space_id         INTEGER NOT NULL REFERENCES space(id),
  name             TEXT,
  work_path        TEXT NOT NULL,
  path             TEXT NOT NULL UNIQUE,
  agents_md_id     INTEGER NOT NULL REFERENCES agents_md(id),
  teach_style_id   INTEGER REFERENCES teach_style(id),
  enable_make_card INTEGER NOT NULL DEFAULT 1,
  review_topic_id  INTEGER REFERENCES topic(id),
  created_at       TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE UNIQUE INDEX pi_session_singleton_ta
  ON pi_session(space_id)
  WHERE space_id = 0;
```

| 字段 | 说明 |
| --- | --- |
| `space_id` | 归属收纳容器；容器类型通过 `space.type` 判断。学习、复习、助教都统一使用这一条父级关系。 |
| `name` | 这次对话在干什么。**AI 唯一有权命名的东西**，首轮结束后由后端独立发起一次 LLM 调用生成，不在会话内走工具（避免污染学习上下文）。用户可改。Pi 官方无自动标题能力，这是自建的。 |
| `work_path` | 本次 Pi Session 独占的工作目录。`AGENTS.md`、`style.md`、JSONL 与该对话私有文件都位于此目录，不能与同一 Space 的其他 Pi Session 共用。 |
| `path` | JSONL 绝对路径，位于 `work_path` 内，文件名由 Pi 根据 `<时间戳>_<sessionId>.jsonl` 生成。`sessionId` 形如 `pi-teacher-pi-session-id-42`（`pi_session.id` 派生，见 ADR-0024）。`SessionManager.create()` 返回后立即 `getSessionFile()` 取得，**不需要回填**：路径在构造时就定了，延迟的只是写盘。 |
| `agents_md_id` | 本次对话用哪套提示词。开对话时从 `space.type` 匹配的模板里选，投影成当前 `work_path/AGENTS.md`。这个外键是历史追溯凭据。 |
| `teach_style_id` | 本次对话用哪种风格。可空，空表示不注入风格。投影成当前 `work_path/style.md`，开会话时与全局 `USER.md` 合并成一段 `appendSystemPrompt`（见「用户偏好注入」）。**可在对话运行期修改**（ADR-0031）：修改后重新投影 `style.md`，并按稳定 ID 重开会话让新的系统提示词生效；重开保留 JSONL 路径、历史与已选模型，运行中修改返回 409，助教对话返回 403。 |
| `enable_make_card` | 制卡开关。与 `space.type` 组合覆盖「新学 / 新学不制卡 / 复习 / 复习不制卡」四种意图。助教对话不看此字段，工具层直接拒绝制卡。**可在对话运行期修改**：工具裁决与 Briefing 每次都实时读取本字段（`server/src/tools/context.ts`），因此改库即刻生效，无需重开会话。 |
| `review_topic_id` | 复习对话的主题过滤，`null` = 不限主题；非复习对话必须为 `null`，由路由层校验。 |

一个 Space 允许多个并发 Pi Session。因为每个 Pi Session 拥有独立 `work_path`，不会再发生 `AGENTS.md`、`style.md` 或 JSONL 的目录覆盖。

文件系统访问不由业务层按 Pi Session 做权限隔离；Docker 是部署隔离边界，远程沙箱由独立 skill 负责。学习、复习、助教之间的业务差异只由工具控制层强制，例如助教禁止制卡和复习写入操作。

**子代理会话不建记录。** 资料抓取子代理（见 ADR-0016）的 jsonl 也会落在 Pi Session 目录体系中，但 `pi_session` 表只记录用户直接参与的对话。理由回到数据库职责：子会话既不需要前端渲染，也不涉及卡片管理，建行只会让每个列表查询都得带一个排除条件。

代价是要靠文件系统识别它们：子会话的 jsonl header 里有 `parentSession` 字段指向父会话文件。排查抓取失败时，扫描工作区目录、按这个字段匹配即可找到对应子会话。清理旧子会话同理——按 header 判断，不查库。

## topic

```sql
CREATE TABLE topic (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  name              TEXT NOT NULL UNIQUE,
  description       TEXT,
  request_retention REAL NOT NULL DEFAULT 0.9,
  maximum_interval  INTEGER NOT NULL DEFAULT 365,
  created_at        TEXT NOT NULL DEFAULT (datetime('now'))
);
```

| 字段 | 说明 |
| --- | --- |
| `name` | 全局唯一。可细化到任意粒度，如「后端」「Java」「JVM」。制卡时 AI 读现有列表优先复用，避免同义词泛滥。 |
| `description` | 给 AI 做归类判据。「Java」可写「Java 语言核心、JVM、并发、集合框架、IO 等」。 |
| `request_retention` / `maximum_interval` | FSRS 参数，主题级配置。核心算法可要 95% 保留率，边缘知识 80% 即可。 |

另两个 FSRS 参数由代码固定写入、不建列：`learning_steps = []`、`relearning_steps = []`——**关闭多步学习**，任何判定路径最短间隔 24h，一张卡一天最多出现一次。这与「一轮复习对话 = 每张卡判一次」的节奏一致（默认的 1m/10m 当天重弹与批量对话式复习不匹配），也让 `card_schedule` 不需要 `ts-fsrs` 5.x 新增的 `learning_steps` 列（该字段恒为 0，不持久化）。`enable_fuzz` 用 ts-fsrs 默认值（开启，打散到期时间聚集）。将来某个 Topic 想要当天重弹，在 WebUI 给它单独开即可——这正是 FSRS 参数做成主题级的原因。

## card

```sql
CREATE TABLE card (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  topic_id            INTEGER NOT NULL REFERENCES topic(id),
  front               TEXT NOT NULL,
  back                TEXT NOT NULL,
  status              TEXT NOT NULL DEFAULT 'proposed',
  reason_and_remark   TEXT,
  created_at          TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (status IN ('proposed', 'normal', 'deleted'))
);
```

| 字段 | 说明 |
| --- | --- |
| `front` / `back` | 正面（问题）与背面（参考答案或评价标准）。 |
| `status` | 卡片状态，三档，见下。 |
| `reason_and_remark` | AI 写的补充说明与制卡原因。取代了原来的溯源字段——「为什么造这张卡」用一段话讲清楚，比存一个消息 id 更有用，也不用去解析 jsonl。 |

### status 三档

| 值 | 含义 | 谁写入 |
| --- | --- | --- |
| `proposed` | 待用户审批的候选卡 | 制卡工具固定写这个值 |
| `normal` | 已确认，参与复习 | 用户在 WebUI 确认时，或用户手动建卡时 |
| `deleted` | 软删除 | 删卡工具、用户删除操作 |

**AI 没有真正的建卡与删卡权限，只能改状态。** 制卡工具固定写 `proposed`，删卡工具固定写 `deleted`，两者都不做物理写入或物理删除。这让暴露给模型的工具面变得很小，也让误操作可恢复。

**读取只认 `normal`。** 到期队列、卡片总数、复习统计一律带 `status = 'normal'` 条件。候选卡只出现在待审批列表，软删除的卡只出现在回收站视图。

`DEFAULT 'proposed'` 是有意的保守取值：遗漏赋值时最坏结果是多一张待审批的卡，而不是未经确认的卡直接混进复习队列。用户手动建卡时显式传 `normal`——手动创建本身即用户意图，不需要再确认（见 ADR-0009）。

### 与 card_schedule 的关系

`card_schedule` 行在卡片转为 `normal` 时才创建，`proposed` 状态的卡没有调度状态——它还不参与复习，凭空给一个 FSRS 初始状态没有意义，还会让「到期卡片数」这类统计需要额外排除条件。

软删除**不删** `card_schedule` 行。这样从回收站恢复时，复习进度原样回来。

### 软删除对 FSRS 的额外好处

`review_log` 通过 `ON DELETE CASCADE` 引用 `card`。软删除不触发级联，所以已删除卡片的复习记录仍然保留。这些记录对 FSRS 参数优化依然是有效样本——用户的记忆规律不因为删了某张卡而改变。

物理删除只发生在用户明确清空回收站时，那时才会级联带走 `review_log`。

不再保留的卡片字段：

**`answer_mode`** — 评价方式交给 AI 判断，这才是灵活性所在。硬编码三档（open_ended / exact / code）反而限制了模型：同一张卡在用户答得完整时该夸，答得含糊时该追问，这些都不是枚举能表达的。需要类型特定的信息（rubric、复杂度要求）就写进 `back` 或 `reason_and_remark`，模型自己看得懂。`metadata` 一并去掉，同理。

**`source_message_id`** — 长对话后从 jsonl 里定位某条消息性能很差（要全文扫描），而拿到原文的实际收益很低。

**`source_pi_session_id`** — 同上，`reason_and_remark` 已经承载了它的意义。

**`source_essence_path`** — ADR-0039 将精华作为独立学习产出，卡片不再保存文件路径关联，也不新增替代关联或来源跳转。旧库初始化时先检查列是否存在，再用 `ALTER TABLE card DROP COLUMN source_essence_path` 幂等移除；其他卡片字段、ID、自增序列、调度、复习日志与精华文件保留。工具与 HTTP 同步不再提供旧来源字段。升级前先备份，回退旧代码需同时恢复升级前的数据库。

## card_schedule

```sql
CREATE TABLE card_schedule (
  card_id        INTEGER PRIMARY KEY REFERENCES card(id) ON DELETE CASCADE,
  state          TEXT NOT NULL DEFAULT 'new',
  due            TEXT NOT NULL,
  stability      REAL NOT NULL,
  difficulty     REAL NOT NULL,
  elapsed_days   INTEGER NOT NULL DEFAULT 0,
  scheduled_days INTEGER NOT NULL DEFAULT 0,
  reps           INTEGER NOT NULL DEFAULT 0,
  lapses         INTEGER NOT NULL DEFAULT 0,
  last_review    TEXT,

  CHECK (state IN ('new', 'learning', 'review', 'relearning'))
);
```

FSRS 状态与卡片内容分离：调度状态每次复习都变，卡片内容基本不变，混一张表会让每次复习重写整行。

| 字段 | 说明 |
| --- | --- |
| `state` | FSRS 四状态。 |
| `due` | 下次到期时间，ISO 8601。到期队列的查询条件。 |
| `stability` / `difficulty` | FSRS 核心参数。 |
| `elapsed_days` / `scheduled_days` / `reps` / `lapses` | FSRS 统计字段。 |
| `last_review` | 上次复习时间。 |

字段命名与 `ts-fsrs` 的 `Card` 对象一致，避免映射层。

## review_log

**保留，用途是优化 FSRS 参数，不是给用户看复习历史。**

```sql
CREATE TABLE review_log (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  card_id        INTEGER NOT NULL REFERENCES card(id) ON DELETE CASCADE,
  rating         TEXT NOT NULL,
  state          TEXT NOT NULL,
  due            TEXT NOT NULL,
  stability      REAL NOT NULL,
  difficulty     REAL NOT NULL,
  elapsed_days   INTEGER NOT NULL,
  scheduled_days INTEGER NOT NULL,
  reviewed_at    TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (rating IN ('Again', 'Hard', 'Good', 'Easy'))
);
```

字段是 `ts-fsrs` 的 `ReviewLog` 结构——**FSRS 参数优化器（`fsrs-optimizer`）需要的就是这个格式的复习序列**，字段对齐可以直接喂给它，不做转换。

砍掉了三类字段：

- **`pi_session_id`** — 那是审计用的（「这次 Again 发生在哪次对话」），优化算法不需要。
- **`ai_evaluation`** — AI 给用户的反馈是一次性的，看完就过去了。FSRS 只吃 `rating`，评语对算法无用。要留痕就让 AI 写进 `card.reason_and_remark`。
- **before/after 双份快照** — 优化器只需要「复习时的状态 + 用户的 rating」。`after` 状态可以由 FSRS 从 before + rating 重算出来，存两份是冗余。

`rating` 由 AI 判定四档。这是 AI 唯一要输出的结构化结果，其余评价都是给用户看的自然语言，不入库。

## glossary

用户**已彻底掌握**的术语。这是全局的用户模型，不属于任何工作区。

```sql
CREATE TABLE glossary (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  term         TEXT NOT NULL UNIQUE,
  definition   TEXT NOT NULL,
  status       TEXT NOT NULL DEFAULT 'proposed',
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (status IN ('proposed', 'normal', 'deleted'))
);
```

四个业务字段，没有任何外键。**表里不出现任何指向工作区、主题、对话的引用**——一旦有，它就退化成某个局部的附属数据，而全局性正是这张表存在的唯一理由。

| 字段 | 说明 |
| --- | --- |
| `term` | 术语本身，全局唯一。「闭包」在 JS 工作区学会了，在 Python 工作区就不必重讲。 |
| `definition` | 简明定义。**用户自己的话，不是教科书定义**——能压缩成一句话正是理解的证明。入库时取工作区 `GLOSSARY.md` 里的那一条，不重写。 |
| `status` | 三档，与 `card` 同构，见下。 |

### 与工作区 GLOSSARY.md 的分工

两者是不同的东西，不是同一份数据的两处存储：

| | 当前 Pi Session `GLOSSARY.md` | `glossary` 表 |
| --- | --- | --- |
| 范围 | 单个 Pi Session | 全局，跨所有 Space |
| 门槛 | 本次对话中用到、约定了口径就写 | **彻底搞懂**才入库 |
| 作用 | 本次对话的标准语言，统一讲解与练习的用词 | 全局用户模型，让 AI 知道用户的知识底座 |
| 谁写 | 模型直接编辑文件 | 模型调工具提议，用户确认（见 ADR-0005） |
| 会不会变 | 随对话推进频繁增改 | 只增，很少改 |

一个术语先出现在当前 Pi Session 的 `GLOSSARY.md`（约定口径），学明白之后才被提议进 `glossary` 表（沉淀为能力）。**入库不从文件里删掉它**——当前对话仍然可以需要自己的标准语言。

### status 三档

与 `card` 完全同构，理由也一样（见 ADR-0005）：错误的术语记录会持续扭曲讲解——AI 以为用户懂了「协变」，之后讲解都跳过它，用户就一直不懂。

| 值 | 含义 | 谁写入 |
| --- | --- | --- |
| `proposed` | AI 认为用户已掌握，待确认 | 提议工具固定写这个值 |
| `normal` | 用户确认已掌握 | 用户在 WebUI 确认，或用户手动添加 |
| `deleted` | 软删除（用户其实没懂，或定义要重写） | 用户操作 |

模型的查询工具只返回 `normal`。`proposed` 只出现在 WebUI 的待审批列表——未确认的记录不能影响讲解行为（见 ADR-0005）。

### 怎么给模型用：不注入，让它自己查

`glossary` 的内容**一个字都不注入上下文**。全局 `~/pi-teacher/AGENTS.md` 里只写一段引导：

> `glossary` 表中记录了用户当前已掌握的术语，可以通过数据库工具读取，用这些信息优化教学方法。

模型自己判断这一轮要不要查、查什么。讲到一个概念前想确认用户是否已懂，就去查；不需要就不查。

这与 `materials/index.md` 是同一个模式（见「AGENTS.md 自动拼接」一节）：**程序只负责让模型知道有这个东西、怎么取，不替它决定什么时候需要。** 全量注入会挤占预算且大部分无用；按相关性筛选则要求程序猜「这一轮要讲什么」，猜不准还引入一层无法调试的启发式。模型自己判断更准，因为只有它知道这一轮在讲什么。

代价是模型可能忘了查。可接受：忘查的后果是把已懂的东西又讲一遍，属于「这次表现不够好」而不是「数据错了」，按 ADR-0014 的分工归提示词管。

所以 `glossary` 不向文件反向投影，和其他表一样只被工具读写。

### 不加的字段

任何「从哪来」的信息都不加：

- **`topic_id`** — 「用户懂不懂闭包」与主题无关。挂上主题就得回答「同一个术语属于多个主题怎么办」，而这个问题本身就说明分类是错的维度。同名不同义（「引用」在 C++ 和 Java 里不同）靠把术语写具体来解决——`C++ 引用`、`Java 引用`——不靠外键消歧。
- **`source_path` / `session_id`** — 记「在哪个工作区学会的」看似无害，实际上把全局资产绑回了临时容器：工作区删掉后字段悬空，而术语本身依然有效。溯源需求也不真实存在——用户想知道的是「我会不会」，不是「我在哪学的」。
- **`mastered_at`** — `created_at` 就是入库时间，而入库门槛就是「彻底搞懂」，两者同义。
- **`confidence` / 掌握程度分数** — 门槛是二元的：搞懂了才入库。分数会诱导 AI 把半懂的也塞进来，标个 0.6 敷衍过去。

`term` 的唯一约束顺带解决了去重：提议已存在的术语时工具直接拒绝（与 ADR-0017 同一原则，精确匹配归代码）。

## 目录布局

```
~/pi-teacher/
  ├─ AGENTS.md              ← 全局规则：工具调用原则、制卡规则、资料库说明
  ├─ USER.md                ← 全局用户画像与偏好
  │
  ├─ materials/             ← 全局资料库，模型判断正确、可学习后归档，三种会话共用
  │   ├─ index.md           ← 索引，普通 Markdown，模型自己维护
  │   ├─ origins/           ← 原件（内容 / 排版混乱待整理，或需转换的原始资料）
  │   ├─ about-docker/      ← 含图片的 HTML 以文件夹形式存储
  │   │   ├─ index.html
  │   │   └─ imgs/

  │       ├─ lesson1-梯度下降.md
  │       └─ lesson2-反向传播.md
  │

  │

  │
  ├─ learn/
  │   ├─ 2/                 ← 目录名 = learn Space.id
  │   │   └─ pi/
  │   │       └─ 42/        ← 目录名 = pi_session.id
  │   │           ├─ AGENTS.md
  │   │           ├─ style.md
  │   │           ├─ pi-session-user.md   ← 会话级用户偏好，模型自行维护，程序不读
  │   │           ├─ files/               ← 会话文件：用户上传给本会话的原始文件（ADR-0038）
  │   │           ├─ essence/             ← 仅学习默认提供空目录，模型按需维护学习精华（ADR-0039）
  │   │           └─ *.jsonl
  │   └─ 3/
  │       └─ pi/<pi-session-id>/
  │
  ├─ review/

  │       ├─ style.md

  │       └─ *.jsonl

          ├─ AGENTS.md              ← 助教没有 style.md（ADR-0035）
          ├─ pi-session-user.md
          ├─ files/
          └─ *.jsonl                ← 「清除对话」换成新文件，其余保留
```

全局文件与目录由 `seed.ts` 在初始化时幂等补建（只补缺失，不覆盖已有内容）：`AGENTS.md` 写 `server/src/prompts/defaults.ts` 的 `GLOBAL_AGENTS_MD`，`USER.md` 与 `materials/index.md` 写同文件里的占位注释。全局 `AGENTS.md` 仍是文件（不进数据库），设置页「全局 AGENTS.md」直接编辑它；三段基础维护提醒与学习精华追加段存 `setting` 表，缺行读出厂值（ADR-0036 / ADR-0039）。升级资料规范时，既有全局 AGENTS.md 需由用户手工合并，不自动覆盖。

**Pi 会话文件存在 Pi Session 自己的目录**：`SessionManager.create(workPath, workPath, { id })` 把当前 Pi Session 的 `work_path` 同时作为 cwd 与 `sessionDir`，JSONL 平铺在该目录根部。删除 Pi Session（ADR-0037）只删行与 JSONL，目录及其余文件保留。

**会话文件 `files/`**（ADR-0038）：上传接口（`/api/conversations/:id/attachments`，路由名保留「附件」这个动作）把文件原样放进去；发送时 png / jpeg / gif / webp 作为图片块进入消息，其他文件在用户消息末尾以一行「用户上传了文件「名」，路径 files/名（大小）。」告知模型，后端不做内容转换。旧部署的 `attachments/` 由启动时的一次性迁移改名。

**资料归档**（ADR-0039）：`files/` 是待阅读、待判断的输入。模型实际阅读并确认正确、可学习后，规整资料直接移入全局 `materials/`；内容组织或排版混乱的，先将原件移入 `materials/origins/`，再把整理版本放进 `materials/`。`materials/index.md` 由模型记录学习版本与原件的对应路径。判断、移动、整理与索引维护全靠提示词约束，不由后端自动执行；不擅自删除用户文件或覆盖资料库里的已有文件。

**学习精华 `essence/`**（ADR-0039）：仅学习 Pi Session 新建时默认创建空目录，旧学习会话正常打开时幂等补齐，不扫描所有历史目录。先确认原 JSONL 存在，再补目录；`essence` 被普通文件占用时返回 409，原文件保留。助教与复习不自动创建，任何会话已有的精华文件均不删除、不覆盖；删除会话或 Space 也保留工作目录里的精华。正文由模型按需维护，仅学习会话与基础维护提醒同轮追加精华段，制卡开 / 关都适用，卡片不再保存精华路径。

**AGENTS.md 自动拼接**（Pi 从 cwd 向上遍历到根）：

1. `~/pi-teacher/AGENTS.md` — 全局通用规则；
2. 当前 Pi Session 的 `<work_path>/AGENTS.md` — 本次对话选定的提示词。

`materials/index.md` 不由程序渲染进 AGENTS.md，全局 AGENTS.md 里写一段引导让模型自己读。

**用户偏好注入**（ADR-0033）。三份文件、三种通道，优先级会话级 > 教学风格 > 全局：

| 文件 | 谁维护 | 怎么进上下文 |
| --- | --- | --- |
| `~/pi-teacher/USER.md` | 用户（设置 → 用户偏好，或直接改文件） | 开会话时读一次，与 `style.md` 合并成一段 `appendSystemPrompt` |
| `<work_path>/style.md` | 数据库投影（`teach_style`） | 同上，Pi 不会自动发现它 |
| `<work_path>/pi-session-user.md` | 模型在对话中自行创建与维护 | 程序不读不写不投影，只在上面那段里固定加一句引导：存在就先读，用户提出只针对本会话的要求时写进去 |

`USER.md` 与 `style.md` 为空（不存在、空白或只剩初始占位注释）时省略对应标签块；会话级引导块无条件附带（ADR-0036 的维护提醒会让模型「更新到 `pi-session-user.md`」，模型必须事先知道它是什么）。助教目录不投影 `style.md`（ADR-0035），因此永远没有风格块；助教「清除对话」只换 JSONL 文件，`pi-session-user.md` 与上传文件保留。

## 文件与数据库的同步

`AGENTS.md` 和 `style.md` 是数据库的投影，**新开 pi_session 时按选定的模板整份覆盖**：

```
新开对话（用户先选会话类型，再选该类型下的 agents_md 和 teach_style）
  → 插入 pi_session 行，取得 id（如 42）
  → 读 agents_md.prompt   → writeFile('<工作目录>/AGENTS.md', ...)
  → 读 teach_style.prompt → writeFile('<工作目录>/style.md', ...)
  → SessionManager.create(workPath, workPath, { id: 'pi-teacher-pi-session-id-42' })
  → getSessionFile() → 写回 pi_session.path
```

**三种 Space 类型复用同一套会话创建流程**，目录前缀、风格投影与默认产出目录按类型区分：

| Space 类型 | Pi Session 工作目录 | 模板来源 |
| --- | --- | --- |
| `learn` | `learn/<space_id>/pi/<pi_session_id>/` | 用户从 `type = 'learn'` 的模板里选 |
| `review` | `review/pi/<pi_session_id>/` | 用户从 `type = 'review'` 的模板里选 |
| `ta` | `ta/pi/<pi_session_id>/` | 固定取 `type = 'ta'` 的模板，不给用户选 |

复习与助教也各自拥有独立工作目录，不再共用容器目录。复习按所选模板与风格投影 `AGENTS.md` / `style.md`；助教只投影 `AGENTS.md`，不生成 `style.md`（ADR-0035）。只有学习 Pi Session 默认提供空 `essence/`（ADR-0039）。

同一个 Space 下，这次可以用「新学」模板，下次用「新学不制卡」或另一种教学风格；每条 Pi Session 的投影互不覆盖。WebUI 里改模板内容，后续新开的 Pi Session 才使用新内容。

**用户手动改这两个文件我们不管**——下次开对话会被覆盖，不做冲突检测，不做回读合并。数据库单向是源。要换提示词就在 WebUI 里切模板，那会用新内容直接覆盖。

想知道某次对话当时用的是哪套提示词，查 `pi_session.agents_md_id`。文件会被后续对话覆盖，这个外键不会。

分成两个文件而不是拼成一个：`agents_md` 定「做什么」、`teach_style` 定「怎么说话」，两者正交、可自由组合，拼在一起就得为每种组合存一份全文。`style.md` 与 `USER.md` 不靠 AGENTS.md 引导，由程序合并注入（见「用户偏好注入」）。

### 并发隔离

每条 Pi Session 都有自己的目录，因此复习或学习对话并发创建时，不会覆盖彼此的 `AGENTS.md`、`style.md` 或 JSONL。具体的全局材料访问权限仍以沙箱决策为准。

## 助教的「知道当前学习上下文」

前端传当前选中的学习 Space 或 Pi Session 身份，后端按后续注入契约向固定助教 Pi Session 注入必要的上下文；助教自身仍运行在固定 `ta/pi/<pi_session_id>/` 目录。它不能因为收到上下文身份就访问其他 Pi Session 的私有目录。
