要点：
- **`createAgentSessionServices` 参数组装**（行 1949-1985）：`cwd`、`agentDir`、`settingsManager`、`resourceLoaderOptions`（含 `extensionFactories`、`extensionsOverride`、chatOnly 用 `CHAT_ONLY_RESOURCE_LOADER_OPTIONS`）、可选 `resourceLoaderReloadOptions`。信任门控（`projectTrustReloadOptions`）决定是否加载项目扩展。
- **`createAgentSessionFromServices` 参数组装**（行 2008-2016）：`services`、`sessionManager`、可选 `model`/`thinkingLevel`/`scopedModels`/`tools`/`excludeTools`。模型初始值由 `selectInitialModelScope` 计算。
- `startRpcSession` 接收的 `sessionId` 对**新会话是临时的**（`/api/agent/new` 传 `__new__${uuid}`），真实 id 由 Pi 生成（`inner.sessionId`），返回 `realSessionId` 给路由层回写客户端。
- 两个启动锁 `__piStartLocks` / `__piStartingSessionCwds` 都在 `globalThis` 上，防 Next.js dev 热重载丢失状态。

### 1.4 事件订阅与广播机制

- `inner`（AgentSession）自己能 `subscribe(listener)`；`wrapper.start()`（行 272-283）订阅并把事件转发到自己的 `listeners`。
- 外部用 `wrapper.onEvent(listener)` 订阅（SSE 流和 subagent controller 都这么干），返回退订函数。**订阅时立即补发缓冲的 `pendingUiRequests`**（行 471），保证晚到的订阅者不丢已发出的 UI 请求。
- `emit(event)`（行 411-422）逐个派发，单个监听器抛错不影响其他监听器。

### 1.6 并发控制（关键）

**prompt 准入串行化**（`acquirePromptAdmission`，行 424-432）：用 `promptAdmissionTail` 把并发 `send({type:"prompt"})` 串成一个链——每个 prompt 等前一个的 preflight **release** 后才开始。这是悲观锁，只做准入；真正的流式排队由 SDK 处理。

**preflight 两段式 ack**（行 540-632）：
1. `inner.prompt(..., { preflightResult: (success) => ... })` —— 同步校验 + 扩展 preflight 通过后回调 `acceptPreflight()`。
2. `await preflight` 返回 → POST 在 preflight 阶段就返回 `{ success:true, data:null }`（**不等整个 run 结束**）。
3. run 结束后 `.then()` fallback：若 SDK 没调 preflightResult（未来版本/不支持），则等下轮结束才 ack 并发 `prompt_done`；失败且已接受 → 发 `prompt_error` + `prompt_done`。

**结论**：prompt 期间再来 prompt —— 第二个请求在 `acquirePromptAdmission` 处等待；前一个 preflight 落定后，SDK 自行决定第二个是"启动新 run"还是"加入 streaming queue"（`streamingBehavior: steer/followUp` 时走队列）。**bash 运行中发 prompt 直接抛错**（行 546-548）。

其它互斥：
- `bash` 在 `pendingPromptCount>0 || isStreaming || isCompacting || isBashRunning` 时抛错（行 913-915）。
- `fork`/`clone` 在 session 运行中抛错；且 mutating 命令计数 `activeMutatingCommands` 保证 fork/clone 与其它命令不并发（行 519-521）。
- `navigate_tree` 在 bash 运行时禁止。

### 1.7 生命周期管理

- **空闲回收**：`resetIdleTimer`（行 434-447），空闲阈值 **10 分钟**（`10 * 60 * 1000`，行 446）。触发条件：`!isRunning()`；若 `isRunning()` 则重置（除非 `forceShutdownOnIdle`）。`abort`/`abort_bash` 置 `forceShutdownOnIdle=true`，让"stop 后空闲即回收"。
- **shutdown()**：幂等，先等扩展绑定（失败仅告警），发一次 `session_shutdown`（reason:"quit"）给扩展，再 `destroy()`。
- **destroy()**：置 `_alive=false`、清 idle、abortBash、退订、cancel 所有 pending UI、清 widgets、发 `session_shutdown`（若未发）、`inner.dispose()`、回调 `onDestroyCallback`（注册表据此删 Map 条目）。
- **进程退出清理**（`getRegistry`，行 1589-1610）：
  - `process.once("exit", destroy)` —— Node 退出处理器无法 await，同步 destroy 作为最佳努力。
  - `process.once("SIGINT"/"SIGTERM", shutdown)` —— 信号处理走优雅 shutdown。

## 2. 多 session 管理

- **存储**：`globalThis.__piSessions: Map<string, AgentSessionWrapper>`（`getRegistry()`，行 1595-1610）。放 `globalThis` 是为了 Next.js dev 热重载时注册表不丢（HMR 会重建模块但 globalThis 保留）。
- **key**：**真实 session id**（`registerRpcWrapper` 行 1618 `registry.set(sessionId, wrapper)`，其中 `sessionId = wrapper.sessionId = inner.sessionId`，Pi 生成）。客户端持有的也是 `realSessionId`。
- **创建**：`startRpcSession`。已存活→复用；有在途启动锁→合并。
- **销毁**：`onDestroy` 回调从 Map 删除；空闲 10 分钟；`destroyRpcSessionsForCwd(cwd)`（关目录下全部）；进程信号。
- **内存上限**：**没有硬上限**。靠 10 分钟空闲超时 + 前端关闭时关闭。`getRunningRpcSessionIds()` 只列 isRunning 的（`GET /api/agent/running` 轮询用）。
- **启动锁**：`globalThis.__piStartLocks: Map<sessionId, Promise>` —— 同一 id 并发 start 合并为一个 promise（`/api/agent/new` 的临时 key 用 `__new__${randomUUID()}` 避免同毫秒冲突，行 57）。
- **cwd 计数**：`globalThis.__piStartingSessionCwds: Map<cwd, count>` —— `hasBusyRpcSessionForCwd` 判断某目录是否有（正在启动或运行中的）会话。

## 3. 事件类型全集

来源分三层：**SDK 事件**（wrapper 原样转发）、**wrapper 自产事件**（rpc-manager 内部 emit）、**SSE 层自产事件**（agent-event-stream 构造）。OMITTED 的见 `agent-event-wire.ts:26-29`。

### 3.1 SDK 事件（wrapper 转发给前端）

| 事件名 | 何时触发 | 前端拿它干什么 | pi-web 转发? |
|---|---|---|---|
| `agent_start` | agent loop 开始一轮 | 置 `agentRunning=true`、dispatch start、显示 waiting_model 阶段 | ✅ |
| `agent_end` | 一轮结束（一次 prompt 可能多轮，重试/压缩/队列续跑时反复发） | 结束本阶段、`loadSession` 重载上下文/contextUsage/systemPrompt/queuedMessages | ✅ |
| `agent_settled` | 完全空闲（队列清空） | 结束所有 UI 阶段、调度关闭 SSE | ✅ |
| `message_start` | 一条消息开始（user/assistant/toolResult） | `message_start` 快照 → 流式气泡；assistant 走 snapshot，user/toolResult 隐藏 | ✅ |
| `message_update` | assistant 消息流式增量（`assistantMessageEvent`: `text_start/delta/end`、`thinking_*`、`toolcall_start/delta/end`） | 累积文本/思考/工具调用参数（`streaming-message.ts` reducer） | ✅（经 agent-event-wire 投影后） |

| `tool_execution_start` | 工具开始执行 | 添加 running_tools 标签 | ✅ |
| `tool_execution_update` | 工具执行进度 | 更新工具进度条（`getToolExecutionProgress(partialResult)`） | ✅ |
| `tool_execution_end` | 工具执行结束 | 移除 running_tools 标签 | ✅ |
| `queue_update` | steer/followUp 排队消息变化 | 显示排队消息列表 | ✅ |
| `auto_retry_start` | 自动重试开始 | 显示重试信息 `{attempt,maxAttempts,errorMessage}` | ✅ |
| `auto_retry_end` | 自动重试结束 | 清除重试信息 | ✅ |
| `auto_compaction_start` | 自动压缩开始 | 置 `isCompacting` | ✅ |

## 4. SSE 协议细节

### 4.1 客户端发命令的 HTTP 接口

**新会话**：`POST /api/agent/new`
```jsonc
// body
{ "cwd": "/path/to/workdir", "type": "prompt", "message": "..." , "images"?: [...], "streamingBehavior"?: "steer"|"followUp",
  "toolNames"?: string[], "provider"?: string, "modelId"?: string, "thinkingLevel"?: "off"|"minimal"|"low"|"medium"|"high"|"xhigh"|"max" }
```
响应（`app/api/agent/new/route.ts:90-98`）：
```jsonc
{ "success": true, "sessionId": "<real id>", "data": <命令结果|null>,
  "model": { "provider": "...", "modelId": "..." } | null, "thinkingLevel": "..." }
```
非 2xx：`{ "error": string, "code"?: "prompt_rejected", "accepted"?: false }`。校验：`cwd` 必填且 `existsSync(cwd)`；`provider`/`modelId` 必须同给；`set_tools` 的 `toolNames` 必须是 string[]。`type:"ensure_session"` 只建会话不发命令（前端先拿命令列表）。

**已有会话**：`POST /api/agent/[id]`
```jsonc
// body：{ "type": "<command 名>", ...命令字段 }    见 1.5 命令表
{ "type": "prompt", "message": "..." , "streamingBehavior"?: "steer"|"followUp" }
{ "type": "set_tools", "toolNames": ["read","edit","bash", ...] }
{ "type": "abort" }  { "type": "get_state" }  { "type": "steer", "message": "..." } ...
```
响应：`{ "success": true, "data": <结果|null> }`；错误：`{ "error": string, "code"?: "prompt_rejected"|..., "accepted"?: false }`（参考 `lib/agent-client.ts` 的 `AgentCommandError`：`status/code/accepted` 三字段，`code==="prompt_rejected" && accepted===false` 是"prompt 被拒"特判）。

**状态查询**：`GET /api/agent/[id]` → `{ running: bool, state? }`；`GET /api/agent/running` → `{ sessionListVersion, runningSessionIds, completionNotificationSuppressedSessionIds }`。

### 4.2 服务端推的事件 JSON（真实例子）

SSE 帧格式：`data: {json}\n\n`；注释帧心跳：`:\n\n`。`agent-event-wire.ts` 已做过过滤/投影。

```jsonc
// 握手（agent-event-stream.ts:91-95）
{ "type": "connected", "sessionId": "2026-09-03T10-00-00-0000_abc123", "isStreaming": false }
```
```jsonc
// assistant 文本流式（message_update，投影后）：text_start → text_delta* → text_end
{ "type": "message_update", "assistantMessageEvent": { "type": "text_delta", "contentIndex": 0, "delta": "你好，" } }
{ "type": "message_update", "assistantMessageEvent": { "type": "text_end", "contentIndex": 0, "content": "你好，世界" } }
```
```jsonc
// toolcall 流式（投影后带 id/toolName）
{ "type": "message_update", "assistantMessageEvent": { "type": "toolcall_start", "contentIndex": 1, "id": "toolu_01...", "toolName": "bash", "partial": { "content": [ {"type":"toolCall","id":"toolu_01...","name":"bash",...} ] } } }
```
```jsonc
// 工具执行进度
{ "type": "tool_execution_update", "toolCallId": "toolu_01...", "toolName": "bash", "partialResult": "..." }
```
```jsonc
// 会话结束
{ "type": "agent_end" }
{ "type": "agent_settled" }
{ "type": "prompt_done" }
```
```jsonc
// 启动失败
{ "type": "startup_error", "errorMessage": "Failed to start agent: ..." }
```

### 4.3 心跳 / 重连 / 超时参数

| 参数 | 值 | 位置 |
|---|---|---|
| SSE 心跳间隔 | `HEARTBEAT_INTERVAL_MS = 30_000`（注释帧 `:\n\n`，代理/proxy 保活） | `agent-event-stream.ts:13` |
| 连接建立即发一次注释帧 | `:\n\n`（强制刷新响应头） | `agent-event-stream.ts:126` |
| 客户端就绪超时 | `EVENT_STREAM_READY_TIMEOUT_MS = 60_000`（EventSource 打开但 60s 未收到 `connected` → `ready_timeout` → 重连） | `hooks/useAgentSession.ts:169` |
| 重连延迟 | `EVENT_STREAM_RECONNECT_DELAY_MS = 1_000` | `useAgentSession.ts:170` |
| 空闲宽限 | `EVENT_STREAM_IDLE_GRACE_MS = 30_000`（`agent_settled` 后保持流 30s 再放行关闭；等文件落盘/推送） | `useAgentSession.ts:165` |
| 状态轮询对齐 | `AGENT_STATE_RECONCILE_MS = 15_000` | `useAgentSession.ts:166` |
| `startup_error` | 停止重连（`stopRetrying`） | `agent-event-connection.ts:66,153-156,170` |

**`connected` 握手的作用**（`agent-event-connection.ts:149-152`）：EventSource 的 `open` 不代表 agent 就绪——服务端要等 Pi session 真正可订阅 `onEvent` 才发出 `connected`。客户端收到该事件才 `attempt.ready=true; succeed()`（结束就绪 Promise），并在 `readyState===OPEN` 时被 `ensureConnected` 当作已连接。这样冷启动（首次创建 Pi 进程）期间连接不会因 404/空帧被误判。

### 4.4 重连语义与快照补发

- `AgentEventConnection.maintain(sessionId)`（被动重连）：只有 `shouldMaintain(sid)` 为真才保活（session 前/后台、agent running、宽限期内）。
- 服务端 `createAgentEventStream`（`agent-event-stream.ts:23-132`）：先开流，再 await `sessionPromise`；在 listener 装好前的事件先进 `bufferedEvents`，`connected` 发出后顺序 flush；若有进行中的 `streamingMessage`，以 `message_start` 快照补发。因此**重连不漏流**。

## 6. 与我们项目的适配点

### 6.1 自定义 `sessionDir`（会话 jsonl 存到指定目录）

需要改 4 处，核心是把 `SessionManager` 的第二参从 `undefined` 换成我们的目录：

1. **`lib/rpc-manager.ts:1893-1899`** —— 会话打开/创建：
   ```ts
   // pi-web 原样
   if (sessionFile) {
     sessionManager = SessionManager.open(sessionFile, undefined);
   } else {
     if (!cwd) throw new Error("cwd is required for a new session");
     sessionManager = SessionManager.create(cwd, undefined);
   }
   ```
   改为把 `undefined` 换成 `sessionDir`（我们的目录）。注意 `SessionManager.open(sessionFile, sessionDir)`：sessionFile 需是存的相对/绝对路径，sessionDir 是 jsonl 所在目录。
2. **`lib/rpc-manager.ts:1581` 的 `getAgentDir()`** —— 它决定 `~/.pi/agent`（settings/models/auth 等全局配置）。**不要动它**。它返回的默认 sessions 路径 `join(agentDir,"sessions")` 只是"默认"，与我们要传的 sessionDir 无关。真正的挂钩点是 `SessionManager.*` 的第二参。
3. **`lib/session-reader.ts`（重写）** —— pi-web 用 `defaultSessionsDir()`（`join(getAgentDir(), "sessions")`）做 `findSessionPathById` 的目录枚举（行 231 附近）。我们的实现应改为只枚举我们的 sessionDir；`resolveSessionPath` / `cacheSessionPath` / `invalidateSessionListCache` 的缓存语义可参考。`app/api/agent/[id]/route.ts:29` 用 `resolveSessionPath(id)` 在无内存会话时恢复会话，必须能指到我们的目录。
4. **fork/clone 分支**（`rpc-manager.ts:704,709,714,720`）—— 若保留 fork/clone，它们内部也用 `sessionManager.getSessionDir()`（原始 session 的目录，天然正确），以及 `SessionManager.create/open` 传 sessionDir，跟着第 1 点改即可。

> 特别注意：若用 `SessionManager.create(workPath, workPath)`（用户的指定），则 `cwd` 与 `sessionDir` 都是 workPath，这意味着 **jsonl 与 AGENTS.md 同目录**。此时 `findSessionPathById` 枚举路径恰是 cwd 本身，实现更简单。

### 6.2 会话启动前写 AGENTS.md 和 style.md

Pi 的 context file 机制：`resourceLoader.getAgentsFiles()` 从**项目 cwd 向上发现** AGENTS.md/CLAUDE.md 等（pi-web 在 chatOnly 下把它们拼进 system prompt，`rpc-manager.ts:2044`；普通模式下 SDK 自动纳入 system prompt）。所以**文件要写在 session 的 cwd 下，不是 sessionDir 下**。

推荐插入点：**`startRpcSession` 的异步体开头**（`lib/rpc-manager.ts:1918`，`const starting = (async () => {` 之后、`initTheme()` 之前）。理由：
- 此时 `cwd` 已解析（行 1900 `sessionCwd`），文件路径可直接算；
- `createAgentSessionServices`（行 1949）与 `createAgentSessionFromServices`（行 2008）都更晚，SDK 加载 AGENTS.md 发生在 services 创建期间/session_start，**先写文件必然被读到**；
- 这是所有会话的统一入口（新建 + 恢复 + 子代理），一处改动全覆盖。

若走重载路径，SDK 还暴露了 `reload({ beforeSessionStart })` 钩子（pi-web 在 `rpc-manager.ts:1569-1573` 用过），可作为 AGENTS.md 变更后重载会话时重写的钩子。注意：把 style.md 纳入系统提示的办法——要么在 AGENTS.md 中 import 它（Pi 的 AGENTS.md 支持 `@path` 引用），要么像 pi-web 那样用 `appendSystemPrompt` 拼进 exactSystemPrompt。

### 6.3 版本差异：0.84.2（本机） vs 0.84.3（pi-web 用固定版，无 ^）

`package.json:42-45` 四个包全锁 **0.84.3**：`@earendil-works/pi-agent-core`、`pi-ai`、`pi-coding-agent`、`pi-tui`。0.84.2 风险点（按严重度排序）：

1. **`preflightResult` 契约（最危险）** —— `rpc-manager.ts:590-595` 的 prompt ack 依赖 SDK 同步调用 `preflightResult(success)`。pi-web 已带 fallback（行 602-607）：若 SDK 不调回调，则 `.then()` 里才 `acceptPreflight()` —— 意味着 **POST 会阻塞到整轮 run 结束才返回**，前端等不到立即 ack → send UI 卡住。必须在本机 0.84.2 上验证 `AgentSession.prompt()` 签名是否含 `preflightResult`。不含就改走"fire and forget + prompt_done 事件"模型。
2. **`agent_settled` 事件** —— 0.84.3 属于较新事件（IDLE_RESET_EVENT_TYPES 与前端 `case "agent_settled"` 都依赖它）。若 0.84.2 不发，前端"结束判定"退化为 `agent_end` + `prompt_done`（`sdkAgentActiveRef` 逻辑在 `useAgentSession.ts:1092` 处会接不住），需按 0.84.2 实测调整。
3. **`bindExtensions` 存在性** —— pi-web 用 `typeof inner.bindExtensions === "function"` 防御（行 317）。0.84.2 若没有该方法，走 `extensionRunner.setUIContext` 分支（行 344），行为仍可用。
4. **`tools: string[]` 参数** —— 注释（行 1924）"Since v0.68.0, session creation expects string[] tool names"，0.84.2 与 0.84.3 同属 0.84 系列，行为一致，风险低。
5. **`prepareNextTurnWithContext` 猴子补丁**（`installExactSystemPromptContinuation`，行 391-404）—— 依赖 pi-agent-core 的 `PrepareNextTurnContext` 结构与返回形状。小版本若调整字段名会导致 exactSystemPrompt 注入失效（但不会崩）。我们不用 chatOnly 的话可整体砍掉这块。
6. **`SessionManager` 方法集** —— `getHeader/getEntries/getBranch/getLeafId/getSessionFile/getSessionDir/createBranchedSession/isPersisted` 等。0.84.2 若缺（如 `getBranch(entryId)` 带参签名变化），fork/clone 与 `getRpcSessionInfos` 会编译失败。
7. **`getSessionStats()` 返回结构** —— `get_session_stats` 命令依赖其字段形状，改动会影响统计面板。
8. **`setThinkingLevel` 的 xhigh 支持** —— `rpc-manager.ts:770` 已有 deepseek compat 特判，是 0.84.3 的 deepseek 兼容；0.84.2 行为需实测（影响 `xhigh` 是否被 clamp 成 `high`）。

**验证手段**：把 4 个依赖改成 0.84.2 后用 `tsc --noEmit` 编译拷贝出的桥接层代码，API 漂移会立刻以类型错误暴露；再各跑一个 prompt 端到端确认 `preflightResult` 与 `agent_settled` 行为。
