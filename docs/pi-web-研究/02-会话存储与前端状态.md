## 1. JSONL 读取与解析（session-reader.ts）

### 1.1 jsonl → 前端消息的总体管线

Pi 的 jsonl 每行一个 JSON 对象（`FileEntry`），首行固定是 `session` header（`lib/types.ts:3-10`）：

```ts
// lib/types.ts:3-10
export interface SessionHeader {
  type: "session";
  version?: number;
  id: string;
  timestamp: string;
  cwd: string;
  parentSession?: string;   // fork/subagent 的父会话文件路径
}
```

其余行是 `SessionEntry` 联合类型（`lib/types.ts:277-286`）：`message` / `thinking_level_change` / `model_change` / `compaction` / `branch_summary` / `custom` / `custom_message` / `label` / `session_info`。每个 entry 都带 `SessionEntryBase`（`lib/types.ts:12-17`）：`type`、`id`、`parentId`、`timestamp`。

读取入口是 SDK：`SessionManager.open(filePath).getEntries()`（`lib/session-reader.ts:407-410`）。SDK 的 `getEntries()` 是**同步全量读**（1MB buffer 循环 `readSync`，见 SDK `dist/core/session-manager.js:285-296`），把整个文件解析成 entry 数组。**没有流式**。

之后 `buildSessionContext()`（`lib/session-reader.ts:447-478`）做三件事：

1. `sliceActiveBranch()` 从 entries 里抽出"当前活跃分支"；
2. 逐 entry 调 `entryToUiMessage()` 转成 UI 消息；
3. `getSessionSettings()` 沿 parentId 链回溯出生效的 thinkingLevel / model。

### 1.2 id/parentId 树结构：分支与 fork

jsonl 是**线性追加**的，但每个 entry 用 `parentId` 指向其父 entry，从而隐含一棵树。切分支 = 换 leaf：

```ts
// lib/session-reader.ts:487-510（sliceActiveBranch）
export function sliceActiveBranch(
  entries: SessionEntry[],
  leafId: string | null,
  tail: number,
  excludeLeaf = false,
): SessionEntry[] {
  if (tail <= 0) return entries;
  const byId = new Map<string, SessionEntry>();
  for (const e of entries) byId.set(e.id, e);

  let leaf = leafId ? byId.get(leafId) : entries[entries.length - 1];
  if (excludeLeaf) leaf = leaf?.parentId ? byId.get(leaf.parentId) : undefined;
  if (!leaf) return [];
  const chain: SessionEntry[] = [];
  let current: SessionEntry | undefined = leaf;
  while (current && chain.length < tail) {
    chain.push(current);
    current = current.parentId ? byId.get(current.parentId) : undefined;
  }
  chain.reverse();
  return chain;
}
```

要点：
- **默认 leaf**：`leafId` 为空时取文件中最后一个 entry（`lib/session-reader.ts:497`），即"最新写入的就是当前分支"，这正是 jsonl 线性追加 + 树靠 parentId 还原的语义。
- **迭代而非递归**（注释 `lib/session-reader.ts:481-486` 明说：线性会话链长等于 entry 数，递归会爆栈）。
- `tail` 参数实现**分页**：只取最近 N 个祖先；`hasMore = sliced[0]?.parentId != null`（`lib/session-reader.ts:458`）。`excludeLeaf` 用于向上翻页时避免重复 `before` entry（`lib/session-reader.ts:498-500` 注释）。
- 树的完整结构由 SDK 的 `sm.getTree()` 提供，route 里经 `projectTreeForResponse()` 透传给前端 `data.tree`（`app/api/sessions/[id]/route.ts:40`）。
- **fork 是新文件**：header 的 `parentSession` 指向原会话 jsonl 路径（`lib/types.ts:9`）。`loadAllSessions()` 里据此解析出 `relation: { kind: "fork" | "subagent" }`（`lib/session-reader.ts:149-170`）。历史页"浏览到某 entry 再 fork"时前端调 `sendAgentCommand(sid, { type: "fork", entryId })`（`hooks/useAgentSession.ts:1452-1455`）。
- 前端切换分支：`handleLeafChange` → `setActiveLeafId(leafId)` + `loadContext(sid, leafId)`（重拉该 leaf 的消息）+ 通知后端 `navigate_tree`（`hooks/useAgentSession.ts:1476-1485`）。
- **导航目标对齐**：`buildSessionContext` 把 `messages` 和 `entryIds` 一起产出（`lib/session-reader.ts:461-469`，注释："Convert messages and their IDs together to keep fork/navigation targets aligned"），前端 `messages[i]` ↔ `entryIds[i]` 一一对应。

`getSessionSettings()`（`lib/session-reader.ts:412-436`）从 leaf 沿 `parentId` 向根走，遇到 `thinking_level_change` / `model_change` / 带 `provider`+`model` 的 assistant message 就停，得到"该分支当前生效"的模型与思考档位。`leafId === null` 返回全 off/null（空会话）。

### 1.3 compaction 条目的识别与展示

jsonl 里的压缩条目类型是 `compaction`（`lib/types.ts:233-242`）：

```ts
// lib/types.ts:233-242
export interface CompactionEntry extends SessionEntryBase {
  type: "compaction";
  summary: string;
  firstKeptEntryId: string;   // 被保留的最老 entry
  tokensBefore: number;
  details?: unknown;
  fromHook?: boolean;
  usage?: AgentUsage;
}
```

识别：`entryToUiMessage` 的 `case "compaction"`（`lib/session-reader.ts:616-627`）把它转成一个 **`role: "custom"`、`customType: "compaction"` 的 UI 消息**，`display: true`，`details` 里带 `tokensBefore` / `firstKeptEntryId`，`content` 是摘要文本：

```ts
// lib/session-reader.ts:616-627
case "compaction":
  return {
    role: "custom",
    customType: "compaction",
    content: entry.summary,
    display: true,
    details: {
      tokensBefore: entry.tokensBefore,
      firstKeptEntryId: entry.firstKeptEntryId,
    },
    timestamp: parseEntryTimestamp(entry.timestamp),
  };
```

展示策略的两条关键决策：
1. **历史页保留被压缩的消息**：`buildSessionContext` 注释（`lib/session-reader.ts:452-453`）："History pages retain the original branch order, including compacted messages. SDK context filtering can drop a page's messages when firstKeptEntryId is outside it." 即 pi-web 不做 SDK 式的按 `firstKeptEntryId` 截断，翻页翻到压缩点之前仍能看到原文，只是插一个 compaction 摘要气泡（前端另有 `lib/compaction-summary.ts` 解析 `<read-files>/<modified-files>` 尾部元数据段）。
2. **`branch_summary`**（探索过分支又返回时 Pi 写入的摘要，`lib/types.ts:243-250`）被转成一条 **user role**、斜体前缀的文本消息（`lib/session-reader.ts:628-634`）：`*The conversation briefly explored another branch and returned with this summary:*\n\n${entry.summary}`。
3. **统计不缩水**：`computeSessionStats`（`lib/session-stats.ts:110-123`）遍历**全部** entry，compaction/branch_summary 上的 `usage` 也累计。注释（`lib/session-stats.ts:98-109`）解释动机：压缩只追加摘要条目、被摘要的历史仍在文件里，所以全文件聚合是单调递增的；只按活跃上下文算会在压缩后表现为"计数器被重置"。

运行中压缩状态由 SSE 事件 `compaction_start` / `compaction_end` / `auto_compaction_start` / `auto_compaction_end` 驱动 `isCompacting` / `compactResult`（`hooks/useAgentSession.ts:1254-1270`）。

### 1.4 大文件性能：全量 or 流式？缓存？

- **单会话详情：全量同步读，无会话级内容缓存。** `getSessionEntries` 直接 `SessionManager.open(filePath).getEntries()`（`lib/session-reader.ts:407-410`），SDK 同步读整个文件。每次 `GET /api/sessions/[id]` 都重新 open + 读全文件。缓解手段是**限制响应体积**而非限制读取：
  - `tail` 参数（默认 50，上限 1000）只把最近 N 个 entry 转成消息（`app/api/sessions/[id]/route.ts:44-45`、`app/api/sessions/[id]/context/route.ts:18-19`）；
  - `deferThinking=1`：历史 thinking block 置空并打 `deferred: true` 标（`lib/session-reader.ts:605-614`），展开时再按需取；
  - `deferMedia=1`：toolResult 里的 base64 图片换成懒加载 URL `/api/sessions/{id}/entries/{entryId}/tool-result-image?blockIndex=n`（≤10MB 且 mime 在白名单内），否则直接丢弃并插一条 `[N tool result images omitted...]` 文本（`lib/session-reader.ts:538-583`，阈值 `lib/tool-result-images.ts:1-9`）。
- **有界的头部/关系读取**：`readBoundedLines` / `readBoundedTailLines`（`lib/session-reader.ts:24-83`）用 `openSync + readSync` 只读前 N 字节/N 行或尾部 N 字节，用于 header（64KB/1 行）、parent 关系（256KB/2 行）、尾部结果（256KB）。避免为了一行 header 读整个文件。
- **会话列表：持久化增量索引**（见第 2 节），这是主要的大文件性能防线。
- **缓存体系**（全部挂 `globalThis`，dev hot-reload 安全，`lib/session-reader.ts:215-225`）：

| 缓存 | key | 失效策略 |
|---|---|---|
| `__piSessionListCache`（列表结果） | 无 key，整体缓存 | TTL 30s（`SESSION_LIST_CACHE_TTL_MS`，`lib/session-reader.ts:227`）；`invalidateSessionListCache()` 递增 generation 并清空（`lib/session-reader.ts:314-317`） |
| `__piSessionPathCache` | sessionId → 文件路径 | 写侧维护一致性（`cacheSessionPath` 双向缓存互斥清理，`lib/session-reader.ts:361-383`）；`invalidateSessionPathCache(sessionId)`（`lib/session-reader.ts:385-394`） |
| `__piPathToSessionIdCache` | sessionPathKey(path) → sessionId | 同上，双向 |
| `__piWebScanIndex`（扫描器指纹索引） | 文件路径 → {size, mtimeMs, info} | 见 2.3 |

- **并发去重**：`listAllSessions` 用 in-flight promise + generation 防抖（`lib/session-reader.ts:187-212`）；若扫描期间被失效（generation 变了），丢弃本次结果并递归重扫（`lib/session-reader.ts:194-199`，注释：旧实现"返回 stale 结果导致刷新竞态与成功刷新无法区分"）。

### 1.5 工具调用 entry 的形态与关联

工具调用**不是独立 entry**，而是 assistant message 的 content block：

```ts
// lib/types.ts:48-54（ToolCallContent，assistant content 的一种 block）
export interface ToolCallContent {
  type: "toolCall";
  toolCallId: string;
  toolName: string;
  input: Record<string, unknown>;
  /** Client-only buffer for streamed tool input. Never persisted to session files. */
  rawInput?: string;
}
```

工具结果则是独立 entry，消息 role 为 `toolResult`，靠 `toolCallId` 关联回 assistant 的 toolCall block（`lib/types.ts:97-104`）：

```ts
// lib/types.ts:97-104
export interface ToolResultMessage {
  role: "toolResult";
  toolCallId: string;
  toolName?: string;
  content: (TextContent | ImageContent)[];
  isError?: boolean;
  details?: unknown;
  ...
}
```

序列化到 jsonl 时，一条 `message` entry 长这样（示意）：

```jsonc
{"type":"message","id":"e-12","parentId":"e-11","timestamp":"...",
 "message":{"role":"assistant","provider":"anthropic","model":"claude-...",
   "content":[{"type":"text","text":"..."},{"type":"toolCall","toolCallId":"call_1","toolName":"read","input":{"path":"a.txt"}}],
   "stopReason":"toolUse","usage":{...}}}
{"type":"message","id":"e-13","parentId":"e-12","timestamp":"...",
 "message":{"role":"toolResult","toolCallId":"call_1","toolName":"read","content":[{"type":"text","text":"file content..."}]}}
```

兼容层：`normalizeToolCalls()`（`lib/normalize.ts:38-60`）把历史/异构写法的 toolCall block 归一化——`toolCallId` 兼容 `id`，`toolName` 兼容 `name`，`input` 兼容 `arguments`（`lib/normalize.ts:24-36`）。`entryToUiMessage` 对每个 message entry 都过一遍（`lib/session-reader.ts:599-600`）。流式版 `normalizeStreamingToolCalls` 额外保留 `rawInput`（`lib/normalize.ts:19-22`，兼容 `partialJson` / `partialArgs` / `customInput`）。

`session-title.ts` 的 `sanitizeTitleMessages`（`lib/session-title.ts:168-209`）反着用这层关联：把**没有对应 toolResult 的 toolCall block 删掉、没有对应 toolCall 的 toolResult 删掉**（见 3.4），保证发给 LLM 的消息序列合法。

## 2. 会话列表扫描（session-list-scanner.ts）

### 2.1 目录发现与文件名规则

- **根目录**：`join(getAgentDir(), "sessions")`（`lib/session-list-scanner.ts:301`；`getAgentDir()` 来自 SDK，默认 `~/.pi/agent`，可被 env `PI_CODING_AGENT_DIR` 覆盖，SDK `dist/config.js:411-417`）。
- **目录枚举**：sessions 下**所有一级子目录**（含 symlink）都算项目目录（`enumerateSessionFiles`，`lib/session-list-scanner.ts:179-202`）。注意：SDK 写入时用的目录名是 `--<encoded-cwd>--`（SDK `dist/core/session-manager.js:242-246`：`--${resolvedCwd.replace(/^[/\\]/, "").replace(/[/\\:]/g, "-")}--`），但 scanner 不假设这个命名——任何子目录都会被扫。
- **文件名规则**：目录下所有 `*.jsonl`（`lib/session-list-scanner.ts:195`）。SDK 生成的文件名是 `${fileTimestamp}_${sessionId}.jsonl`，`fileTimestamp = timestamp.replace(/[:.]/g, "-")`（SDK `dist/core/session-manager.js:665-667`）。**按 id 反查路径**时用的是后缀匹配 `_${sessionId}.jsonl` + header 校验（见 `lib/session-reader.ts:261-297`）。

### 2.2 列表元数据来源

`scanSessionFileInfo()`（`lib/session-list-scanner.ts:91-177`）对**单个文件做全量流式扫描**（`createReadStream` + `readline`，逐行 JSON.parse）：

| 元数据 | 来源 | 需要读整个文件吗 |
|---|---|---|
| `id` / `cwd` / `created` / `parentSessionPath` | 首行 session header | 只需首行 |
| `name` | 最后一条 `session_info` entry 的 `name`（`lib/session-list-scanner.ts:117-122`） | 需要（但通常是文件早段，循环里遇到就更新） |
| `messageCount` | 统计所有 `type === "message"` 行 | **需要全量** |
| `modified` | 最后一条 user/assistant message 的 timestamp（`activityTimeOf`，`lib/session-list-scanner.ts:75-88`）；无消息则 header 时间；再不行用文件 mtime | **需要全量** |
| `firstMessage` | 第一条 user message 的文本（`extractTextContent` 拼接 text block，`lib/session-list-scanner.ts:59-73, 140-142`） | 通常只需前几行 |
| token / 成本 | **不在列表里**。列表 API 只给 `path/id/cwd/name/created/modified/messageCount/firstMessage/relation`（`loadAllSessions`，`lib/session-reader.ts:156-172`）。token/成本只在**单会话详情**里给（`computeSessionStats`，`app/api/sessions/[id]/route.ts:56`） | 列表不读 |

即：**列表项的 messageCount 和 modified 必须全量读 jsonl 才能算**——这正是增量索引存在的理由（指纹不变就复用上次结果，只有 stat 调用）。

`attachSessionProjectInfo()`（`lib/session-reader.ts:111-129`）再按 cwd 解析 git 项目根（`resolveProject`，含 worktree 检测），补充 `projectRoot` / `projectKey` / `branch`。

### 2.3 缓存机制：双层

**第一层：内存 + 磁盘持久化的指纹索引**（`lib/session-list-scanner.ts`）：
- `globalThis.__piWebScanIndex`：`Map<path, { fp: {size, mtimeMs}, info: ScannedSessionInfo }>`（`lib/session-list-scanner.ts:25-33`）。
- 持久化到 `~/.pi/agent/pi-web-session-index.json`（`indexFilePath()`，`lib/session-list-scanner.ts:224-226`；`APP_NAME="pi"` → 文件名前缀 `pi-web-`），版本号 `INDEX_FORMAT_VERSION = 1`，**原子写**（`writePrivateFileAtomicSync`，`lib/session-list-scanner.ts:275-291`，queueMicrotask 合并写）。
- `listSessionsIncremental()`（`lib/session-list-scanner.ts:298-361`）流程：加载持久索引 → 枚举文件 → 删掉已消失的（stale）→ 并行 `stat` 全部文件 → 指纹（size+mtimeMs）相同直接复用缓存 info，不同的进 `changed` 列表 → **并发池（`MAX_CONCURRENT_SCANS = 10`，`runPool`，`lib/session-list-scanner.ts:204-217`）**重扫 → 有变更/删除则持久化索引 → 按 modified 降序排序输出。
- 已知局限（作者自己注明，`lib/session-list-scanner.ts:1-4`）：size/mtime 指纹**检测不到"同尺寸 + mtime 被还原"的编辑**；需要时换 content hash。

**第二层：结果级缓存 + 失效（session-reader.ts）**：
- `listAllSessions()`（`lib/session-reader.ts:177-213`）：30s TTL 结果缓存 + in-flight promise 并发去重 + generation 失效。
- `invalidateSessionListCache()`（`lib/session-reader.ts:314-317`）调用点（生产代码）：
  - `lib/rpc-manager.ts` 12 处：会话创建、`set_session_name`、删除等所有落盘变更后（如 `lib/rpc-manager.ts:276, 611, 685, 722, 750, 773, 783, 791, 932, 1709, 1724`）；
  - `app/api/sessions/[id]/route.ts:128`（PATCH 改名）、`:208`（DELETE 删除）；
  - `app/api/sessions/[id]/auto-name/route.ts:37`（自动命名写回后）；
  - `listAllSessions({ force: true })` 自身（`lib/session-reader.ts:178`，即 `GET /api/sessions?force=1`）。

**API 层合并**：`GET /api/sessions`（`app/api/sessions/route.ts:16-42`）= 磁盘扫描（`listAllSessions`）+ 内存中的运行时会话（`getRpcSessionInfos()`），`mergeSessionLists` 以磁盘为准覆盖同 id 项并按 modified 排序（`lib/session-reader.ts:131-140`），响应还带 `sessionListVersion`（generation）和 `runningSessionIds`。

## 3. 自动标题生成（session-title.ts）——完整分析

### 3.1 触发时机

**纯手动，无自动触发。** 前端唯一入口是顶栏"生成标题"按钮（`components/AppShell.tsx:1285-1360`）：

- 按钮 disabled 条件：`!selectedSession || selectedSession.transient || !hasMessages || autoNameStatus.kind === "naming"`（`components/AppShell.tsx:1292`）；`hasMessages` 同时看 `sessionStats.userMessages > 0` 或 `messageCount > 0`（`components/AppShell.tsx:1287-1291`，注释：压缩后当前上下文可能不含 user 消息，需参考文件级统计）。
- 点击 → `handleAutoName()`（`components/AppShell.tsx:806-835`）→ `POST /api/sessions/{id}/auto-name`。状态机 `autoNameStatus: idle | naming | success | error`，success 1.8s / error 5s 后回到 idle；切换会话即重置（`components/AppShell.tsx:837-839`）。
- 服务端 route（`app/api/sessions/[id]/auto-name/route.ts:7-45`）：`resolveSessionPath(id)` 找文件 → 复用或 `startRpcSession` 启动一个 AgentSession（内存中活的会话对象）→ `waitUntilReady()` → `generateSessionTitle(session.inner)` → `session.inner.setSessionName(title)` 落盘 → `invalidateSessionListCache()`。若命名期间会话被关闭返回 409。

（另有手动 `/name <name>` 命令走 `set_session_name`（`hooks/useAgentSession.ts:1624-1629`），与本机制共用 `setSessionName` 落盘路径。）

### 3.2 模型与调用方式

**走 Pi SDK 的 `Agent`，用当前会话同款模型，不是独立 LLM 请求。** 核心思路（`lib/session-title.ts:41-45` 注释）："Build a temporary Agent configuration whose provider-facing prefix matches the source Agent"——构造一个**临时 Agent**，继承源会话的 systemPrompt / model / thinkingLevel / messages / streamFn / convertToLlm / transport 等（`buildSessionTitleAgentOptions`，`lib/session-title.ts:46-70`），但把所有 tools 换成 **shadow tools**——名字、schema、描述全部保留，`execute` 一律抛错（`createShadowTools`，`lib/session-title.ts:32-39`）：

```ts
// lib/session-title.ts:32-39
function createShadowTools(tools: AgentTool[]): AgentTool[] {
  return tools.map((tool) => ({
    ...tool,
    execute: async () => {
      throw new Error("Tools cannot be executed while generating a session title");
    },
  }));
}
```

这样 prompt 里的工具前缀与原会话一致（缓存友好），但模型任何 toolCall 都执行不了。`generateSessionTitle`（`lib/session-title.ts:211-255`）流程：

1. `sourceAgent.waitForIdle()`——必须等源会话空闲（所以命名按钮只在非运行时可用是隐含前提，但代码层硬等）。
2. `sanitizeTitleMessages(messages)` 清洗消息序列（见 3.4）。
3. 无 user 消息（也无 compactionSummary）直接抛错 "The session has no user messages to name"（`lib/session-title.ts:217-221`）。
4. 构造临时 Agent，注入清洗后的消息。
5. **请求注入方式**（`lib/session-title.ts:225-233`，注释 `lib/session-title.ts:73-76`：避免向 provider 发两条连续 user 消息）：
   - 若最后一条是 user（运行中的会话通常以"正被回答的 user 消息"结尾）：把 TITLE_PROMPT **追加进这条 user 消息**（`appendTitleRequestToTrailingUser`，`lib/session-title.ts:77-89`），然后 `temporaryAgent.continue()`；
   - 否则：`temporaryAgent.prompt(TITLE_PROMPT)` 作为新 user 消息发。
6. `Promise.race([runPromise, 90s 超时])`（`TITLE_TIMEOUT_MS = 90_000`，`lib/session-title.ts:9`）。
7. `getAssistantResult()`（`lib/session-title.ts:138-166`）从**临时 Agent 新增的** assistant 消息（`agent.state.messages.slice(historyLength)`）倒序找第一条非空文本；`stopReason === "error"` 则抛 `errorMessage`；同时提取 usage。

### 3.4 结果清洗（parseGeneratedSessionTitle）

`parseGeneratedSessionTitle`（`lib/session-title.ts:108-136`）对模型原始输出做多级防御性清洗，**必须贴原文**：

```ts
// lib/session-title.ts:108-136
export function parseGeneratedSessionTitle(raw: string): string {
  let value = raw.trim();
  const fenced = value.match(/^```(?:json|text)?\s*([\s\S]*?)\s*```$/i);
  if (fenced) value = fenced[1].trim();

  if (value.startsWith("{")) {
    try {
      const parsed = JSON.parse(value) as { title?: unknown };
      if (typeof parsed.title === "string") value = parsed.title.trim();
    } catch {
      // Fall back to plain-text cleanup below.
    }
  }

  value = value.split(/\r?\n/, 1)[0] ?? "";
  value = value.replace(/^(?:session\s+title|title|标题)\s*[:：-]\s*/i, "");
  value = stripWrappingQuotes(value).replace(/\s+/g, " ").trim();
  value = value.replace(/[。.!]+$/u, "").trim();

  if (!/[\p{L}\p{N}]/u.test(value)) {
    throw new Error("The model did not return a usable session title");
  }

  const characters = Array.from(value);
  if (characters.length > MAX_TITLE_LENGTH) {
    value = characters.slice(0, MAX_TITLE_LENGTH).join("").trim();
  }
  return value;
}
```

清洗项：剥 ```` ``` ```` 围栏 → 尝试 JSON `{title}` → 只取首行 → 去 `Title:`/`标题:` 前缀（`stripWrappingQuotes` 兼容中英日引号对，`lib/session-title.ts:91-106`）→ 压空白 → 去尾部句号（含中文句号）→ 无字母数字即判失败 → 按**字符**（`Array.from`，代理对安全）截断到 `MAX_TITLE_LENGTH = 80`。

`sanitizeTitleMessages`（`lib/session-title.ts:168-209`）清洗**输入**消息序列：每个 assistant 消息只保留"后面紧跟了对应 toolResult"的 toolCall block；toolResult 只有在前面 assistant 保留了这个 id 时才保留；被清空 content 的 assistant 消息整体删除。防的是：发两条连续 user 消息、或发未闭合的 toolCall/toolResult 对导致 provider 400。

### 3.5 生成结果存哪

**写回 jsonl，不是单独文件。** `session.inner.setSessionName(result.title)`（`app/api/sessions/[id]/auto-name/route.ts:36`）→ SDK `AgentSession.setSessionName` → `SessionManager.appendSessionInfo(name)`（SDK `dist/core/session-manager.d.ts:227`）→ **追加一条 `session_info` entry 到会话 jsonl**（`{type:"session_info", name, id, parentId, timestamp}`，类型见 `lib/types.ts:272-276`）。读取侧取**最后一条** session_info 的 name（SDK `dist/core/session-manager.js:849-857`；pi-web scanner 同逻辑 `lib/session-list-scanner.ts:117-122`）。改名字典是追加式的，历史名字留在文件里但读取只看最新。写回后 `invalidateSessionListCache()` 让列表刷新。

### 3.6 失败 / 超时处理

- **超时**：`TITLE_TIMEOUT_MS = 90_000`；`Promise.race` 超时先 `temporaryAgent.abort()` 再 reject "Session title generation timed out"（`lib/session-title.ts:237-252`）；catch 分支里也 `abort()` 并 `await runPromise.catch(() => {})` 吞掉后续错误。
- **模型报错**：assistant `stopReason === "error"` → 抛 `errorMessage`（`lib/session-title.ts:143-145`）。
- **无可用输出**：文本为空 / 无字母数字 → "The model did not return a usable session title" / "The model did not return a session title"（`lib/session-title.ts:127-129, 165`）。
- **会话被关闭**：route 层 409 "The session was closed while its title was being generated. Please try again."（`app/api/sessions/[id]/auto-name/route.ts:29-34`）。
- **前端**：所有错误都归到 `autoNameStatus: {kind:"error", message}` 显示 5 秒（`components/AppShell.tsx:832-834`）；不会回滚已有标题（因为只在成功后写）。

### 3.7 usage

`GeneratedSessionTitle.usage`（`lib/session-title.ts:21-30`）返回这次命名的 token 花费（input/output/cacheRead/cacheWrite/total），route 原样透传（`app/api/sessions/[id]/auto-name/route.ts:38`），前端可用于展示成本。注意：临时 Agent 的消息**不在**源会话消息里，命名请求不会污染会话历史（`agent.state.messages.slice(historyLength)` 只读临时 Agent 自己的新增部分）。

## 4. useAgentSession 的 reducer 与状态管理

### 4.1 state 结构总览

`useAgentSession`（`hooks/useAgentSession.ts:271-2056`，2056 行）是巨型 hook，state 分四块：

**a) 持久会话数据（useState）**：

- `loading / error / activeLeafId`。

**b) 流式专用 reducer**（`lib/streaming-message.ts`）：


### 4.2 四种 action 对 state 的影响（streamReducer）

```ts
// lib/streaming-message.ts:124-144
export function streamReducer(state: StreamingState, action: StreamAction): StreamingState {
  switch (action.type) {
    case "start":
      return { isStreaming: true, streamingMessage: null };
    case "snapshot": {
      const message = normalizeStreamingToolCalls(action.message);
      return message.role === "assistant"
        ? { isStreaming: true, streamingMessage: message }
        : state;
    }
    case "delta":
      return applyDelta(state, action.event);
    case "end":
      return INITIAL_STREAMING_STATE;
    default:
      return state;
  }
}
```

| action | 语义 | state 变化 |
|---|---|---|
| `start` | 一轮生成开始 | `isStreaming=true`，清空 `streamingMessage`（防上一轮残留气泡） |
| `snapshot` | 收到 `message_start` 的 assistant 全量快照（replay/重连场景 server 先发一份当前累计消息） | 经 `normalizeStreamingToolCalls` 后整体替换 `streamingMessage`；非 assistant 忽略 |
| `delta` | `message_update` 的 token 级增量 | `applyDelta` 按 `contentIndex` 定位 block 就地更新（见 4.3） |
| `end` | `message_end` / `agent_end` / 一轮结束 | 重置为 `INITIAL_STREAMING_STATE`（气泡消失，落成 `messages` 里的一条） |

dispatch 调用点：`start` 在 `agent_start` 事件与 `handleSend`（`hooks/useAgentSession.ts:1066, 1320`）；`snapshot` 在 `message_start` 且 role=assistant（`:1146`）；`delta` 在 `message_update`（`:1154`）；`end` 在 `connected` / `agent_end` / `agent_settled` / `message_end` / `settleUiStage` / `handleSend` 失败路径（`:1050, 1075, 1199, 834, 1396`）。

**注意 `snapshot`/`delta`/`end` 只管理"正在流式的那一条消息"**；已落库消息的更新走 `setMessages`（`message_end` 里 append 完成消息，`agent_end` / `prompt_done` 里整体 `loadSession` 重拉）。

### 4.3 token 级 delta 的拼接（applyDelta）

所有 delta 都带 `contentIndex`，`updateContentBlock`（`lib/streaming-message.ts:27-43`）复制 content 数组、按 index 替换一个 block（不可变更新，配合 React 渲染）。事件类型（`lib/streaming-message.ts:45-122`）：

- `text_start`：在 `contentIndex` 处确保存在 `text:""` block（`current?.type === "text" ? current : {type:"text", text:""}`）；
- `text_delta`：**`text: current.text + event.delta` 字符串追加**；当前 block 不是 text 则返回 null（丢弃，防错位）；
- `text_end`：用 `event.content` **整体覆盖**（server 的权威终值，纠正增量累计的误差）；
- `thinking_start` / `thinking_delta` / `thinking_end`：同 text 三段式，作用于 `thinking` 字段；
- 未识别类型返回原 state（`default: return state`）。

`text_end` 覆盖而非追加是重要设计：delta 传输可能丢/重，end 事件携带完整内容做校准。

### 4.4 toolcall_start / toolcall_delta 的累积

```ts
// lib/streaming-message.ts:82-111
case "toolcall_start":
  return updateContentBlock(state, event.contentIndex, (current) => {
    if (current?.type === "toolCall") {          // snapshot 里已有 → 只补 id/name
      return {
        ...current,
        toolCallId: event.id ?? current.toolCallId,
        toolName: event.toolName ?? current.toolName,
        rawInput: current.rawInput ?? "",
      };
    }
    if (typeof event.toolName !== "string") return null;
    return {                                      // 新建空 toolCall block
      type: "toolCall",
      toolCallId: event.id ?? "",
      toolName: event.toolName,
      input: {},
      rawInput: "",
    };
  });
case "toolcall_delta":
  return updateContentBlock(state, event.contentIndex, (current) => (
    current?.type === "toolCall"
      ? {
        ...current,
        toolCallId: event.id || current.toolCallId,
        toolName: event.toolName || current.toolName,
        rawInput: (current.rawInput ?? "") + event.delta,   // 增量 JSON 参数
      }
      : null
  ));
```

- 工具参数流式期间只累积 **`rawInput` 字符串**（server 端 partial JSON），**不解析**；每个 delta 还带 `id`/`toolName` 兜底（某些 provider 的 start 事件缺 id）。
- `toolcall_end`（`lib/streaming-message.ts:112-118`）用 `event.toolCall.arguments`（已解析对象）替换为正式 `input`。
- `rawInput` 是**前端专用字段，永不落库**（`lib/types.ts:53` 注释）；`normalizeStreamingToolCalls` 保留它、`normalizeToolCalls` 剥掉它。
- `toolcall_start/delta` 事件里的 `id/toolName` 是 pi-web 的 wire 层从 server 事件 `partial.content[contentIndex]` 里投影出来的（`lib/agent-event-wire.ts:30-56`），兼容 `id`/`toolCallId`、`name`/`toolName` 双写法。

### 4.6 乐观 UI：立即显示与回滚

`handleSend`（`hooks/useAgentSession.ts:1281-1398`）：

1. 本地立即构造 `userMsg`（含 images 时为 content block 数组），`setMessages((prev) => [...prev, userMsg])`（`:1307-1314`），同时记录 `optimisticUserMessageKeyRef.current = userMessageKey(userMsg)`（`:1315`）——key = `{text, images 签名}` 的 JSON（`lib/prompt-recovery.ts:36-48`，图片以 mime+data 拼签）。
2. 置 `agentRunning=true`、`agentPhase=waiting_model`、`dispatch({type:"start"})`、滚动锚定。
3. 发 `POST prompt`。
4. **成功路径**：`message_end` 里 server 回放这条 user 消息 → 若与乐观消息同 key，保持不变（去重）；若 key 不同（server 改写），替换末尾；若不是相邻乐观消息（steering 队列投递），追加。随后 `agent_end` / `prompt_done` 触发整体 `loadSession` 权威重载。
5. **失败回滚**（`catch`，`:1365-1397`）：
   - `definitivelyRejected = !promptRequestStarted || isPromptRejectedError(e)`——请求根本没发出去，或服务端明确拒绝。
   - 明确拒绝：从 `messages` 里 `lastIndexOf(userMsg)` 删掉乐观气泡（引用相等定位，`:1376-1381`）、弹 error notice、**`restoreSubmission(message, images, composerDraftKey)` 把内容放回输入框**（草稿恢复系统 `lib/draft-store.ts`）、清 optimistic key；但仍保留 SSE 一会并 `reconcileAgentState`（另一 tab 可能真有 run 在跑，注释 `:1385-1388`）。
   - **歧义失败**（发出去了但响应丢了）：**不回滚**，走 `waitForPromptSettlement` 轮询服务端，让服务端状态决定（防回滚掉实际已接受的消息造成"消息消失"）。

## 7. 适配点：自定义会话目录 `~/pi-teacher/learn/5/*.jsonl`

我们的存储：**平铺** `~/pi-teacher/learn/5/*.jsonl`（无按 cwd 编码的子目录层）。Pi 默认：`~/.pi/agent/sessions/<dir>/*.jsonl`，其中 `<dir>` 由 SDK 写入时定为 `--<encoded-cwd>--`（SDK `dist/core/session-manager.js:242-246`）。所有依赖默认路径的位置：

### session-list-scanner.ts

| 位置 | 代码 | 改法 |
|---|---|---|
| `lib/session-list-scanner.ts:301` | `const sessionsDir = join(getAgentDir(), "sessions");` | 改为 `~/pi-teacher/learn/5`（可经 env/配置注入） |
| `lib/session-list-scanner.ts:179-202`（`enumerateSessionFiles`） | 枚举 sessionsDir 的**一级子目录**再取其中的 `.jsonl` | 平铺结构：直接 `readdir(sessionsDir)` 过滤 `.endsWith(".jsonl")`，删掉目录层循环（`dirs`/`join(sessionsDir, dir.name)`） |
| `lib/session-list-scanner.ts:224-226`（`indexFilePath`） | `join(getAgentDir(), "pi-web-session-index.json")` | 索引落盘点随数据目录走，如 `~/pi-teacher/learn/5/.index.json`（或独立 cache 目录，避免污染会话目录） |

### session-reader.ts

| 位置 | 代码 | 改法 |
|---|---|---|
| `lib/session-reader.ts:230-232`（`defaultSessionsDir`） | `join(getAgentDir(), "sessions")` | 唯一的目录源头函数——**改这一个即可让 `resolvePathWithinDefaultSessions` 生效于新根** |
| `lib/session-reader.ts:234-246`（`resolvePathWithinDefaultSessions`） | 以 defaultSessionsDir 为根做相对路径逃逸校验 | 逻辑不变，根变了自动生效 |
| `lib/session-reader.ts:248-298`（`findSessionPathById`） | `readdir(sessionsDir)` 遍历**所有项目子目录**，文件名后缀 `_${sessionId}.jsonl` 匹配 + header 校验 + 查重 | 平铺后无需目录层：直接 `readdir(根)` 按后缀匹配；若我们的文件名不含 sessionId（如 `5.jsonl`），改用 **header.id 校验为主**（现逻辑里 header 校验本来就是 authoritative，`:250-251` 注释）甚至直接建立 path↔id 缓存初始化时一次全扫 |
| `lib/session-reader.ts:300-312`（`findSessionIdByPath`） | `resolvePathWithinDefaultSessions(filePath)` 限定默认目录内 | 根替换后自动生效；若需支持目录外路径需放宽 |
| `lib/session-reader.ts:142-175`（`loadAllSessions`） | 调 `listSessionsIncremental()`（间接依赖目录）+ `attachSessionProjectInfo`（对每个 cwd 跑 git 解析） | 前者随 scanner 改；后者若 cwd 无意义直接删，`SessionInfo.cwd` 可置为固定值或省略 |

### 附带依赖（同链路）

- `app/api/sessions/[id]/route.ts:148-203`（DELETE）：`dirname(filePath)` 假设"兄弟文件在同一目录、可能有 parent 关系"——平铺后无 parent 概念，整段级联可删。
- SDK 侧（若我们自己写 jsonl）：`SessionManager` 的 `persist` 会把文件写到 `getSessionDir()`（即 `getDefaultSessionDirPath(cwd)`）。我们不走 SDK 写入时无需处理；若走 SDK，可用 env `PI_CODING_AGENT_SESSION_DIR`（SDK `dist/config.js:398` 定义但 session-manager 用的是 `sessionDir` 构造参数/env，视版本确认）或构造时传入自定义 `sessionDir`。
- `readSessionRelationEntries`（`lib/session-reader.ts:96-109`）按 `parentSession` 读父文件——我们无 fork，可删。
- 其他 `getAgentDir()` 使用点（auth.json、subagent settings、web-push 等，`lib/provider-credential-store.ts:79` 等）不在会话读取链路上，按各自功能取舍。

**一句话总结适配**：目录结构差异集中在 `defaultSessionsDir()`（reader）与 `sessionsDir` 硬编码（scanner:301）+ 两处"目录→文件"两层枚举（scanner:179-202、reader:248-298）。把根目录抽成配置、把两层枚举压成一层、砍掉 parentSession/fork/project-info 分支，其余逻辑（指纹索引、entry 转换、流式 reducer、乐观 UI、标题生成）可基本平移。
