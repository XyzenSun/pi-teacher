# 不用 MCP：能力扩展只有 skill 和插件两个载体

> 状态：「沙箱走插件」一条被 ADR-0040 取代——沙箱改为 skill（`sbx` CLI 随镜像分发）。本文其余结论（不用 MCP、载体只有 skill 与插件、生图走 skill）不变。

agent 能力的扩展载体收敛为两个：**skill**（教模型一套做事方法、包 CLI 的使用说明）和**插件**（结构化工具、流程介入、上下文修改）。MCP 明确不引入——包括不装社区 MCP 桥接插件。

本 ADR 提前关闭了 ADR-0006 与 ADR-0023 留下的「skill 还是 MCP，接入时再定」的口子。

## Pi 官方立场就是 No MCP

Pi 的 README（0.84.2）原文：

> **No MCP.** Build CLI tools with READMEs (see Skills), or build an extension that adds MCP support.

MCP 在 Pi 生态里不是原生能力，是一个**社区插件补出来的洞**。要用 MCP，等于先装一个第三方桥接插件，再多一类 server 配置面、多一个进程边界——每一层都是依赖与故障面。

## 能力上确实差不多

逐项对过我们需要的能力（判据表见 `docs/pi的插件skill与mcp分工.md`）：

- 结构化参数、不让模型写 shell——插件 `defineTool` 完整支持，我们的 15 个业务工具全部这么实现
- 拦截/阻止/修改工具调用、改 system prompt、注入上下文、访问当前 session——只有插件能做，MCP 本来就不行
- 教模型用 CLI 的方法与边界——skill 的本职

MCP 的差异化卖点是**多 Agent / 多 IDE 复用、远程部署、独立进程与认证**——这些对单用户 Docker 本地部署全部用不上。这与否决 Next.js 是同一个逻辑：为用不上的卖点背一层额外抽象。真出现「第二个客户端要复用沙箱工具」的需求，Pi 插件本身就跨宿主可装，能力并不被锁死在 pi-teacher 里。

## Consequences

- 载体集合收敛为：普通应用模块（数据库访问、FSRS 计算等确定性逻辑）、skill、插件、数据库 prompt 表（用户在界面增删改的行为片段，ADR-0006 的这条不变）。
- **生图走 skill**（ADR-0023 里「接入时再定」就此关闭）：skill 内部完成调用、下载落盘，返回本地路径。
- **沙箱走插件**（ADR-0015 里「倾向 MCP」作废）：插件封装沙箱 API 为结构化工具，切换商业沙箱只改插件内部实现。
- `docs/pi的插件skill与mcp分工.md` 里的 MCP 判据行成为历史参考。
- 未来若某个外部服务确实需要给非 Pi 的客户端用，到时再单独评估——不为假想需求预先付抽象成本。

## Considered Options

### 装社区 MCP 桥接插件

否决。多一个第三方依赖（官方不维护桥）、多一类配置面、多一个进程边界，换来的能力插件和 skill 已覆盖。桥接插件的质量与维护节奏不由我们控制。

### 自研 MCP 支持

更不值——等于为「不引入 MCP」这件事专门写一个 MCP 层。
