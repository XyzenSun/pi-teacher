# 会话存储与业务库物理分离，业务库用 SQLite

Pi 自己管理会话存储，业务确定性数据（学习空间、卡片、调度状态、复习记录、偏好、学习产出）独占一个 SQLite 库。两者只通过 `workspaceId`、会话与消息标识关联，不做跨库 join，业务代码不直接读写 Pi 的表或会话文件。

分离的理由是迁移史独立（会话结构随 Pi 版本演进，业务结构归项目自己管）、写锁互不干扰（SQLite 写锁是库级的，模型每轮高频追加消息不应与业务写抢同一把锁）、数据价值不同（会话历史可归档可重建，业务数据不可再生）。两个存储同放一个数据目录，备份仍是打包目录。

## Considered Options

- **同一个 SQLite 文件、分表命名空间**：曾以「卡片写入与会话写入可同事务」为理由。这条理由不成立——二者之间不存在需要原子性保护的不变量。若进程恰在工具执行后崩溃，最坏结果只是会话文本提到某张卡片而卡片表没有该行；卡片列表以业务库为准、调度只读业务库，该不一致不破坏调度正确性。用架构耦合换一个假收益，否决。
- **直接上 Postgres**：并发写、全文检索、多用户当前都用不上，却要多维护一个服务进程、备份不再是拷文件。与「纯自用单用户，不为尚不存在的需求堆基础设施」的定位冲突，否决。

## Consequences

- 单用户不等于单写者：多个空间同时开对话、流式回答期间在另一标签页确认卡片、后台生成到期队列都是真实并发。这些写落在不同表的不同行，分库不引入一致性问题。
- 需要展示卡片来源原文时，按溯源标识回查会话存储，而不是跨库查询。
- 更换 Pi 的会话存储后端时，业务库不需要改动。
