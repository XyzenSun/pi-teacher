# 卡片去重：精确匹配归代码，语义判断归模型

去重是硬约束，写在制卡工具里（见 ADR-0014）。但「重复」有两层含义，必须拆开处理。

**精确重复归代码。** 同一 Topic 下，`front` 归一化后完全相同则拒绝。归一化包括去首尾空白、压缩连续空白、统一中英文标点、忽略大小写。这防的是机械错误：模型在一次对话里重复调用工具、用户手动建卡时没注意已有同样的卡、导入笔记时同一条出现两次。

**语义重复归模型。** 制卡工具的返回值里带上该 Topic 下已有卡片的 `front` 列表。模型看到相近的，自己决定是放弃、改写成互补的角度、还是提议合并（见 ADR-0012 的合并卡机制）。

去重范围按 **Topic**，不按工作区。同一块知识在两个工作区学到，也不该出现两张卡——卡片归属 Topic 而非工作区，这是 ADR-0010 的既定边界。

## Considered Options

### 嵌入向量 + 余弦相似度阈值

技术上完全可行，代价很低。2000 张卡用 1024 维 float32 只占 8 MB；暴力计算余弦相似度是几毫秒的事，不需要 ANN 索引。若单独建 `card_embedding` 表、正常业务查询永不 JOIN 它，对现有检索性能的影响为零。

否决的理由不在性能，在判据本身：

- **语义相似不等于重复。** 「什么是闭包」和「闭包在实际开发中的典型应用」相似度可能有 0.88，但它们是两张合法的卡——一张考概念，一张考应用。而「JVM 内存分为哪几块」和「Java 堆和栈的区别」相似度可能只有 0.75，却高度重叠。阈值调不出来：调高了漏，调低了误杀合法卡。误杀是用户完全看不见的——模型被工具拒绝后换个话题就走了。
- **规模不需要它。** 一个 Topic 下大约 50–200 张卡，把所有 `front` 直接给模型看，它自己就能判断，而且判断质量比余弦距离高——它理解语义，不只是算向量夹角。
- **给高频路径引入外部依赖。** 每次制卡都要调一次嵌入 API，多一处延迟、一处失败模式、一份成本。
- **违反 ADR-0014 的分工。** 「这两张是不是重复」是判断，不是可验证的事实。硬塞进代码，就是用阈值假装客观。

### 完全不做代码层去重，全交模型

模型会犯机械错误——同一轮里重复调工具、忘了刚才建过。这类错误是确定性的、可验证的，正是代码该管的。全交模型意味着这类脏数据会真的进库。

### 用 `front` 的模糊匹配（编辑距离、n-gram）

比精确匹配宽一点，比向量窄一点，但同样面临阈值问题，且中文分词后的 n-gram 效果不稳定。收益不足以抵消复杂度。

## Consequences

- 制卡工具的签名里，拒绝条件只有一个：归一化后 `front` 已存在于同 Topic。实现是一次字符串比对，无外部依赖。
- 制卡工具**成功时**也返回已有卡片的 `front` 列表（限同 Topic，按创建时间倒序，最多几十条），让模型有机会事后察觉相似并主动处理。这条列表进主会话上下文，但一个 Topic 几十条问题句的开销可接受。
- 模型判断相似后的处理方式——放弃、改角度、合并——全在提示词里，可迭代。
- 向量能力不做在去重上，但**留给别处**：`materials/` 与 `essence/` 的语义检索（几十万字语料，关键词搜索不够，且「相似」就是想要的结果）、复习时把相近卡片排在一起（相似度只是排序依据，判错了顶多顺序不理想）、「你学过 X，它和 Y 有关」的联想提示。这三个都是功能而非约束，容错性高。
- 如果首版跑起来后确实出现「模型反复造相似卡」的问题，再回来加向量去重——那时有真实数据可以调阈值，而不是凭空猜。
