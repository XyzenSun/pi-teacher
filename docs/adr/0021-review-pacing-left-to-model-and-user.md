# 复习节奏交给模型与用户，代码不设限

复习相关的「多少」「多久」「积压了怎么办」这类节奏问题，**代码一律不做限制**。取卡工具只暴露一个 `nums` 参数，由模型结合用户偏好自主决定；到期队列如实累积，不调整 FSRS 算出的 `due`；不做每张卡耗时的预估与配额。

## 为什么不由代码定

这些都是**偏好**，不是**不变量**（见 ADR-0014 的分工）。一批取 10 张还是 30 张，取决于用户今天有多少时间、这个 Topic 有多难、上次复习感觉如何——这些信息只有对话里的模型和用户知道，代码里的任何默认值都只是猜。

而且用户和模型在对话里就能把节奏偏好沉淀下来：写进全局 `USER.md`（「我每次复习不超过 20 分钟」）或工作区 `USER.md`（「这个主题的卡我想一次多刷几张」）。模型下次读到，自然会调整 `nums`。这条路径已经存在，不需要为它建配置项。

## 三个具体问题的处理

**一批取多少张。** 取卡工具签名里只有 `nums`（和 `review_topic_id`，来自 `pi_session`）。全局 AGENTS.md 的工具调用原则里写明：结合用户偏好与对用户能力的判断自主选择。不给默认值以外的任何限制。

**积压怎么办。** 停用一周回来堆了两百张——这种情况会经常发生，不是异常。队列保持原样，不顺延、不限量、不改 `due`。模型看到积压量，自己决定这次取多少、按什么顺序（比如先清最逾期的）。逾期天数如实累积进 `elapsed_days`，这对 FSRS 参数优化是有效样本，改写它反而污染数据。

**耗时预估。** 不做。「一张概念卡半分钟、一张算法卡五分钟」这种差异模型自己看得出来，不需要程序从 `review_log` 里统计出一个数再喂给它。

## WebUI 直接复习：不经模型的第二条路径

用户应当能**不用 AI 辅助**，在 WebUI 里自己翻卡、自己选记忆程度。这是一条独立于对话的复习路径。

它存在的理由是节奏自主的另一面：有时候用户只想快速刷十张卡，不想跟模型聊。而且它是最简单的复习形态，任何时候都可用——模型服务挂了、API 额度用完了，卡片照样能复习。

对设计的影响：**Rating 有两个来源**——模型在复习对话里判定（见 ADR-0019），或用户在 WebUI 里直接点选四档之一。两者写入同一张 `review_log`，走同一套 FSRS 调度。`review_log` 不需要记录来源——FSRS 只关心 rating，用户自评与模型判定对算法是等价的输入。

## FSRS 参数优化不设记录数门槛

手动触发的参数优化（见 `todo.md`）不检查 `review_log` 条数，0 条也允许调用。

FSRS 优化器自身对样本量有内置处理：记录不足时它不会给出偏离默认值的权重。我们在外面再加一层「至少 N 条才能点」的门槛，只是重复它的逻辑，还得自己猜 N 该是多少。

**待验证**：`fsrs-optimizer` 在空输入或极少输入时是返回默认权重还是抛异常。若是后者，接口层要捕获并给用户一句「记录不足，参数未改变」，而不是让按钮报错。这个验证很便宜，实现时跑一次即知。

## Considered Options

### 每日复习上限 + 积压顺延

Anki 的做法。否决：顺延要改写 `due`，等于篡改 FSRS 的输出，`elapsed_days` 失真后参数优化会被误导。而「每天最多 N 张」这个 N 又回到了「代码猜偏好」的老问题。

### 按预估耗时凑批

从 `review_log` 的 `reviewed_at` 间隔统计每张卡的历史耗时，取卡时凑「大约 20 分钟一批」。否决：需要真实数据积累才能工作，冷启动时没用；且模型自己看卡片内容就能判断难度，不需要统计数字。

## Consequences

- 取卡工具签名：`(nums, review_topic_id?) → Card[]`，只返回 `status = 'normal'` 且 `due` 已到的卡，按 `due` 升序（最逾期的在前）。挑选逻辑仅此一条，其余归模型。
- 判定工具接受一批 `(card_id, rating)`（见 ADR-0018、ADR-0019）；WebUI 直接复习走同一个后端接口，只是调用方是前端而非模型。
- 节奏偏好的载体是 `USER.md`，不建配置表、不加 `pi_session` 字段。
- 复习界面需要两个入口：「和 AI 一起复习」（开复习对话）与「自己刷卡」（不开对话，直接操作卡片）。
- FSRS 参数优化的接口层要处理「记录不足」的情形，具体行为等验证优化器实际表现后定。
