# 复习是一场批量对话，不是逐卡问答

复习工具的形态定为：**取一批到期卡 → 组织成一场对话 → 批量判定回写**。不做「取一张卡、判定、更新、再取下一张」的单卡循环。

## 为什么不是单卡循环

单卡循环把复习变成了一次次独立的问答，模型看不到这一批卡之间的关系，只能机械地一问一答。而复习的价值恰恰在关联：三张卡都在讲 JVM 内存，模型应该能把它们串成一个连贯的追问链，从「分几块」问到「为什么这么分」再到「哪块会 OOM」。一张一张地喂，这个串联能力就废了。

它也让「按主题分组组织，不把不同领域混着问」（ADR-0014 列为提示词职责）无从落地——模型手里只有一张卡时，没有可分组的对象。

## 批量的代价与边界

批量意味着一批卡的判定结果在对话结束时才回写。中途关掉页面，这一批的复习就白做了。这是可接受的：

- 复习本身是一次有始有终的活动，不像学习对话那样可能横跨几天。
- 到期队列的数据没有被破坏，下次打开重新取一批就是。
- 反过来，逐卡即时回写会产生「答了三张就跑」的半场状态，`card_schedule` 里出现一批 `due` 参差不齐的卡，反而更难处理。

一批取多少张、如何分组、每日上限与积压怎么办，属于队列策略，仍未定（见 open-questions）。这条决策只固定工具的形状。

## 对工具签名的影响

- **取卡**：入参是 `review_topic_id`（来自 `pi_session`，`null` = 不限主题）与批量大小，返回一批 `status = 'normal'` 且 `due` 已过的卡。挑选逻辑归代码，不由模型筛（见 ADR-0014）。
- **判定**：入参是一组 `(card_id, rating)`，一次调用提交整批。四档 Rating 的判定规则仍未定（见 open-questions），但无论怎么定，它产出的都是这个结构。
- 合并卡按整组知识的掌握度给一个 Rating（见 ADR-0012），在批量模型下天然成立——它本来就是一次调用里的一个条目。

## Consequences

- 复习界面是一个对话窗口，不是卡片翻面器。这与「AI 出题、判定、给反馈」的复习模板（见 `数据库设计.md` 的 `agents_md` 预置行）一致。
- 若某批卡没有全部判定（模型漏了几张），代码按「没提交就不算复习过」处理：不写 `review_log`，不动 `card_schedule`，这些卡下次继续到期。漏判是不完美，不是错误数据。
- 一场复习对话对应一个 `pi_session` 行，`space_id = 2`，跑在 `review/` 目录。这与现有 schema 无冲突。
