# 优先 Docker 部署，代码执行用远程沙箱

> 状态：被 ADR-0027 收口——远程沙箱若接入，只走 skill 或插件，不走 MCP。
> 状态：「沙箱的接入形态是插件」被 ADR-0040 取代——已按 skill 接入（`sbx` CLI，esbuild 单文件随镜像分发）。
> 状态：基础镜像由 `node:22-slim` 升至 `node:24-slim`（PRD `docs/tasks/preproduction-readiness.md` §3.6：开发与全部验证都在 Node 24 上跑，依赖 `engines` 均 ≥ 22）；slim vs alpine 的结论不变。

系统默认假设运行在容器环境中，并在该约束下设计。同时兼容宿主机直接部署。

## 为什么优先容器

Pi 官方刻意不做权限控制——它的设计哲学是「用 OS 级隔离（容器 / 虚拟机）保障安全」。我们接受这个设计，而不是试图在应用层加权限沙箱。

对学习助手而言，大部分操作（对话、制卡、复习）不改造环境，危险操作只在算法题执行代码时出现。因此容器足以覆盖主要安全需求。

## 容器环境的约束

- **不能嵌套运行 Docker**。算法题的代码执行不能依赖容器内再起容器。
- **不能假设宿主机文件系统可访问**。资料文件、图片、数据库都在容器内或挂载卷。
- **持久化数据必须显式挂载**。业务库、Pi 会话存储、用户上传的资料，这些必须落在明确的挂载点，而非容器的临时文件系统。

## 代码执行用远程沙箱

算法题的代码执行不在本地跑，而是调用远程沙箱服务（Judge0、Piston、自建等）。理由：

- **避免在镜像里塞运行时**。不为 Python、Java、C++ 各准备一套编译器和依赖，镜像保持轻量。
- **规避嵌套容器问题**。沙箱本身通常也是容器化的，若在容器内再跑会遇到 Docker-in-Docker 的复杂性。
- **执行环境可独立扩展**。新增语言支持只需沙箱服务端配置，不用重构主应用镜像。
- **算法题不是高频操作**。学习与复习占 99% 的时间，代码执行偶尔发生，网络延迟可接受。

沙箱的接入形态是**插件**（MCP 已否决，见 ADR-0027）——插件封装沙箱 API 为结构化工具，日后支持多家沙箱或本地沙箱，切换只改插件内部实现。

## 兼容宿主机部署

用户若选择直接在宿主机跑（开发环境、或不愿用容器的部署），系统仍能工作。此时：

- Pi 的权限控制缺失意味着工具可以访问宿主机的完整文件系统与进程，需自行承担风险。
- 远程沙箱仍是代码执行的首选，除非用户明确配置本地执行后端。

宿主机部署不是推荐路径，文档和默认配置均以容器为准。

## 基础镜像用 node:22-slim，不用 alpine

实测数据（脚本见 `scripts/probe-base-images.sh`）：

| | `node:22-alpine` | `node:22-slim` |
| --- | --- | --- |
| 基础体积 | 230MB | 325MB |
| 补齐 bash + GNU 工具后 | 238MB | 已自带 |
| `better-sqlite3` | 有 musl 预编译，3 秒装完 | 有预编译，3 秒装完 |
| `python3` | 不自带 | 不自带 |

alpine 的体积优势只有 87MB。这不足以换取 musl 与 BusyBox 带来的差异：

- **BusyBox 缺 GNU 扩展**。实测 `date -d "3 days ago"` 与 `grep -P` 都不支持（`sed -i.bak` 倒是支持了，BusyBox 1.37 已补上）。补装 `coreutils grep gawk` 能恢复，但这正是那 8MB 的来源。
- **包名与 Debian 不同**，`build-base` 而非 `build-essential` 之类。模型写 Dockerfile 时容易照抄 Debian 包名。
- **musl 与 glibc 的运行时差异**（DNS 解析、多线程内存分配）虽然对单用户本地部署影响有限，但它是一类无法在文档里穷举的风险。

原先担心的最大风险是原生模块编译——`better-sqlite3` 若无 musl 预编译包，Dockerfile 就得「装工具链 → 编译 → 删工具链」。实测排除了这一点，两边都有预编译二进制。但即便如此，87MB 依然换不来足够的收益。

两个镜像**都不自带 python3**（slim 剥得比预期狠），所以「哪个自带 Python」不构成选型依据。而我们也不装它，见下节。

`/bin/sh` 在 slim 上是 dash，也不是 bash。Dockerfile 里若要用 bashism，仍需 `SHELL ["/bin/bash", "-c"]`。

## 镜像里只有一个语言运行时

**Node.js 是镜像内唯一的语言运行时**，因为它是应用本身。不装 Python。

每多一个运行时就多一份维护面：另一套包管理（pip 还要面对 PEP 668 的 externally-managed 限制）、另一套版本兼容问题、另一份安全更新来源、镜像里两套标准库。而 Python 在这里能做的事，其他三条路都能做，没有一项非它不可。

工具脚本按复杂度选三条路，都不引入新运行时：

| 路子 | 适用 | 为什么不增加负担 |
| --- | --- | --- |
| **Shell** | 文件搬运、简单管道、调用其他命令 | slim 自带完整 GNU userland |
| **Node（`.mjs`）** | 需要 JSON 处理、异步、调 API、读写数据库 | 运行时已在镜像里 |
| **Go 编译的二进制** | 计算密集、需要严格错误处理、或希望和主应用解耦 | 静态链接零依赖，镜像里只多一个文件 |

### Go 二进制在别的仓库开发

Go 工具**不在本仓库写源码**。单独建仓库，用 GitHub Actions 交叉编译，本仓库只 `COPY` 对应架构的产物。

这样本仓库始终是纯 TypeScript：没有 `go.mod`，没有 Go 工具链，`docker build` 不需要编译阶段，构建时间不受影响。二进制的版本、测试、发布全在它自己的仓库里管，本仓库只认一个版本号。

代价是跨仓库协作——改一个 Go 工具要发版再更新引用。这对「写一次就基本不动」的工具来说不是问题，反而强制了版本纪律。多架构（amd64 / arm64）由 Actions 的 build matrix 出全套，Dockerfile 里按 `TARGETARCH` 选。

### 例外

远程沙箱：用户的算法题代码可以是任何语言，那在沙箱服务端执行，与本镜像无关。

## Consequences

- Dockerfile 是首版交付物之一，不是「后续再做」的扩展项。基础镜像为 `node:22-slim`。
- 数据库路径、Pi 会话存储路径、资料存放路径必须明确且可配置，默认值指向容器卷挂载点。SQLite 单独挂载。
- 算法题执行能力依赖外部沙箱服务，离线环境下该能力不可用——这需在产品层面对用户说清。
- **镜像里只有 Node.js 一个语言运行时**，不装 Python。工具脚本用 Shell、Node 或预编译的 Go 二进制。
- Go 工具需要一个独立仓库 + GitHub Actions 交叉编译流水线。本仓库只 `COPY` 二进制，保持纯 TypeScript、无编译阶段。
- 选 slim 也意味着镜像里有完整 GNU userland，模型在容器内跑 shell 命令时不会遇到 BusyBox 的行为差异。这对一个大量依赖模型调用命令行的系统是实际收益。
- 全局 AGENTS.md 需要写明「镜像内无 Python，写脚本用 Shell 或 Node」，否则模型会默认伸手去拿 python3。
