# 优先 Docker 部署，代码执行用远程沙箱

系统默认假设运行在容器环境中，并在该约束下设计。同时兼容宿主机直接部署。

## 为什么优先容器

Pi 官方刻意不做权限控制——它的设计哲学是「用 OS 级隔离（容器 / 虚拟机）保障安全」。我们接受这个设计，而不是试图在应用层加权限沙箱。

对学习助手而言，大部分操作（对话、制卡、复习）不改造环境，危险操作只在算法题执行代码时出现。因此容器足以覆盖主要安全需求。

## 容器环境的约束

- **不能嵌套运行 Docker**。算法题的代码执行不能依赖容器内再起容器。
- **不能假设宿主机文件系统可访问**。资料文件、图片、数据库都在容器内或挂载卷。
- **持久化数据必须显式挂载**。业务库、Pi 会话存储、用户上传的资料，这些必须落在明确的挂载点，而非容器的临时文件系统。

## 代码执行用远程沙箱

算法题的代码执行不在本地跑，而是调用远程沙箱服务（Judge0、Piston、自建等）。理由：

- **避免在镜像里塞运行时**。不为 Python、Java、C++ 各准备一套编译器和依赖，镜像保持轻量。
- **规避嵌套容器问题**。沙箱本身通常也是容器化的，若在容器内再跑会遇到 Docker-in-Docker 的复杂性。
- **执行环境可独立扩展**。新增语言支持只需沙箱服务端配置，不用重构主应用镜像。
- **算法题不是高频操作**。学习与复习占 99% 的时间，代码执行偶尔发生，网络延迟可接受。

沙箱的接入形态倾向 MCP（见 ADR-0006）——如果日后需要支持多家沙箱或本地沙箱，切换成本低。

## 兼容宿主机部署

用户若选择直接在宿主机跑（开发环境、或不愿用容器的部署），系统仍能工作。此时：

- Pi 的权限控制缺失意味着工具可以访问宿主机的完整文件系统与进程，需自行承担风险。
- 远程沙箱仍是代码执行的首选，除非用户明确配置本地执行后端。

宿主机部署不是推荐路径，文档和默认配置均以容器为准。

## Consequences

- Dockerfile 是首版交付物之一，不是「后续再做」的扩展项。
- 数据库路径、Pi 会话存储路径、资料存放路径必须明确且可配置，默认值指向容器卷挂载点。
- 算法题执行能力依赖外部沙箱服务，离线环境下该能力不可用——这需在产品层面对用户说清。
- 镜像不包含任何语言运行时（Node.js 除外，它是应用本身的依赖）。
