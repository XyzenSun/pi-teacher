# 制卡判据交给模型，用提示词约束

卡片数量必须与用户真正需要保持的知识成正比，而不是与知识领域的大小成正比。Java 后端八股有 500 个知识点，全提议成卡，无论配什么管理界面都会被淹没——界面只能让人更快划过卡片，不能减少卡片。

但「什么值得做成卡」这件事无法用规则表达。原先的判据是「用户在此处失败过」这一可观察事实，它足够硬，代价是把制卡时机绑死在失败瞬间：用户一遍就懂但明确说「这个我想记住」的知识进不来，几个零散事实合起来才有价值的卡也造不出来。

因此判据交给模型，我们只给标准，不给规则：

**内聚、高价值、凝练。**

跟 `essence/` 目录同一条标准。essence 是课程内容的精炼，卡片是 essence 的进一步凝结。一张卡应当是一个完整的知识单元，不是一段摘录，也不是一个知识点的碎片。

制卡质量靠提示词保障，并持续迭代优化。这是明确的取舍：放弃了「判据可机械验证」，换来模型在具体场景里的判断力。

## Considered Options

- **只从真实失败点产生**（原决策）：判据可观察、可解释，但把制卡窄化成了错题收集。用户主动想记的、需要跨轮次归纳的都进不来。且「失败」本身也需要模型判断——追问几轮算不算没懂？边界并不比「值得记」更清晰。否决。
- **用结构化 rubric 约束**（要点数量、字数上限、必须含代码示例等）：看似可验证，实际是把提示词写成配置。不同学科的卡片形态差异极大，rubric 要么宽到无约束力，要么窄到误杀。否决。
- **按学习目标系统性铺满知识点**：产出成体系，但这是在重造现成的八股题库。题库已是红海，不构成差异化。否决。

## Consequences

- 制卡质量取决于提示词质量，这成为需要长期投入的核心资产。提示词存在 `agents_md` 表里，可迭代、可 A/B 对比。
- 卡片来源不再限定于对话中的失败点。模型可以在讲解后、在写完 essence 后、在用户明确要求时提议。
- 用户手动创建入口保留。它满足「用户自己操作卡片」的诉求，不需要引入外部工具（见 ADR-0008）。
- AI 提议仍需用户确认（见 ADR-0005）；手动创建本身即用户意图，直接入库。
- 每张卡带一段 `reason_and_remark`，记录模型为什么造这张卡以及补充说明。这是判据从「可验证的事实」转向「模型判断」之后唯一的可追溯凭据，也让用户在确认时能看懂提议理由。
- 放弃了对制卡行为的机械审计能力。如果卡片质量出问题，排查手段是读 `reason_and_remark` 与优化提示词，不是修改规则。
