# 卡片只从真实失败点产生，另开手动入口

卡片数量必须与用户的薄弱点成正比，而不是与知识领域的大小成正比。Java 后端八股有 500 个知识点，但用户真正记不住的可能只有 50 个。如果把「讲过的重要知识点」都提议成卡，无论配什么管理界面都会被淹没——界面只能让人更快划过卡片，不能减少卡片。

因此卡片有且只有两个来源：

1. **AI 从对话中观察到的真实失败**——用户答错、反复追问才理解、或明说「这个我总记不住」。即 CONTEXT.md 中的 Sticking Point。
2. **用户手动创建**——随时可以把想记的东西存成卡，不必等 AI 提议。

## Considered Options

- **AI 判断「值得长期记忆」就提议，靠用户确认时过滤**：把过滤负担全压给用户。一场长对话后弹出几十条待确认，用户会开始无脑通过或干脆不看——与卡片洪水是同一个结局，只是延后了一步。否决。
- **按学习目标系统性铺满知识点**：产出成体系，但这是在重造现成的八股题库。题库已是红海，不构成差异化。否决。

## Consequences

- 提议的判据是「用户在此处失败过」这一可观察事实，而不是「这个知识点重不重要」这种主观判断。这让 rubric 写得出来，也让提议行为对用户可解释。
- 用户没聊到的盲区不会被覆盖。这是接受的代价：盲区不该靠背卡解决。
- 手动入口满足了「用户自己操作卡片」的诉求，不需要为此引入外部工具（见 ADR-0008）。
- 两个来源的写入路径不同：AI 提议遵循 ADR-0005 需用户确认；手动创建本身即用户意图，直接入库。
