# 模型直接输出四档 Rating，不经中间层归档

复习判定时，模型在工具调用里直接给出 `Again` / `Hard` / `Good` / `Easy` 之一。不做「模型先出评语或分数、再由另一段逻辑映射成四档」的两段式。

## 为什么不要中间层

两段式看起来更可控，实际上是把判断伪装成计算。中间层无论用分数区间还是关键词匹配，都要把「这个回答算不算吃力」压成一个可比较的数，而这个压缩本身就是判断——只是从理解语义的模型手里，转移到了一段不理解语义的映射规则手里。

ADR-0003 已经指出这里的核心陷阱：四档不是百分制的线性映射，核心结论错误就是 `Again`，答对但明显吃力才是 `Hard`。一个打分再映射的中间层几乎必然把 60 分映射成 `Hard`，把 85 分映射成 `Good`，正好落进这个陷阱。模型能同时看到「答错了什么」和「答得多费劲」，直接给档反而更准。

两段式还多一处失败模式：模型的评语与最终落库的档位可能不一致，用户看到「基本正确，稍有卡顿」却发现卡片被判了 `Again`，无从申诉。直接出档，评语和档位来自同一次判断。

## 判定规则归提示词

每一档的含义写在复习提示词的 rubric 里，不写进代码（见 ADR-0014：这是判断，不是可验证事实）。rubric 是需要长期迭代的资产，最初的基线来自 ADR-0003：

- `Again` — 核心结论错误，或答不出
- `Hard` — 结论对，但过程明显吃力、需要提示、绕了弯路
- `Good` — 正常答对
- `Easy` — 立刻答对且毫无迟疑，说明间隔可以拉得更长

代码只做枚举校验：`review_log.rating` 的 `CHECK (rating IN ('Again','Hard','Good','Easy'))` 拦住非法值，除此之外不干预。

## Consequences

- 判定工具的入参是一组 `(card_id, rating)`，批量提交（见 ADR-0018）。除枚举校验外没有转换层。
- 模型给的档位偏松或偏紧，是提示词问题，改 rubric 即可，不动代码。`review_log` 累积的真实数据可以用来回头校准——若某个 Topic 下 `Easy` 占比异常高，通常是 rubric 太宽而不是用户真的都会。
- 评语仍然要给用户看，但它走对话正文，不是判定的输入。前端不需要从评语里解析档位。
- 模型主动提出的特殊调度覆写仍需独立工具与业务校验（见 ADR-0003），不能借 Rating 通道夹带。
