# 行为倾向由提示词表达，硬约束由代码强制

提示词模板之间的差异、教学风格的不同、学习与复习对话的区别——这些区分**几乎都不是代码分支，而是注入给模型的内容差异**。系统不为每种模式写一套独立逻辑，而是用同一套流程配上不同的注入内容。

因此**上下文组装器是核心模块**：它根据对话类型、选定的提示词模板与教学风格、以及当前业务状态（待复习卡数、待确认提议、学习进度），组装出这一轮注入给模型的内容。

## 两类差异必须分开处理

**行为倾向 → 提示词。** 模型可以自行权衡、偶尔偏离也不造成数据损坏的：

- 制卡判据的松紧（见 ADR-0013：这就是为什么「激进制卡」不做成数据库字段）
- 制卡的标准是「内聚、高价值、凝练」（见 ADR-0009）
- 复习对话中制卡要克制，只在暴露新问题或引伸新知识时才做
- 教学风格、追问深度、评价方式
- 复习时按主题分组组织，不把不同领域混着问
- 卡片的评价方式与评级判定（见 ADR-0003：这就是为什么 `answer_mode` 被删掉）

**硬约束 → 代码。** 一旦被违反就产生错误数据或破坏不变量的：

- 制卡开关关闭时——工具层直接拒绝，不能只写在提示词里
- 助教对话不得制卡——工具层直接拒绝
- 卡片的**精确**重复——同 Topic 下 `front` 归一化后相同则工具层拒绝。语义相似归提示词，因为那是判断不是事实（见 ADR-0017）
- 提议必须确认才入库——`card.status` 状态机保证，制卡工具固定写 `proposed`
- 卡片删除是软删除——删卡工具固定写 `deleted`，模型没有物理删除能力
- 到期队列的计算——FSRS 与查询决定，不由模型挑选
- 制卡前必须读取现有 Topic 列表——作为工具的输入要求，而非请求模型「记得先看一眼」

判断准则：**如果模型在某次调用中忽略了这条规则，后果是「这次表现不够好」还是「数据错了」？** 前者归提示词，后者归代码。

## 这条原则如何塑造了 schema

它是好几个字段被删掉的直接理由：

- `card.answer_mode` 三档枚举——评价方式是判断，交给模型（见 ADR-0003）
- `card.metadata`——rubric、题目限制这类内容写进 `back` 或 `reason_and_remark`，模型自己看得懂
- 制卡倾向三档枚举——判据松紧归提示词（见 ADR-0013）

反过来，它也是几个字段被保留或新增的理由：

- `pi_session.enable_make_card`——硬开关，必须能在工具层判定
- `card.status`——状态机是不变量，必须由代码保证
- `review_log.rating`——模型评价与调度计算之间唯一的结构化接口，必须落库

## 静态与动态的注入分工

上下文组装器有两条注入路径，各管一段：

**静态内容走文件投影。** 提示词模板与教学风格在开对话时写成 `AGENTS.md` 和 `style.md`，整份覆盖。它们在一次对话期间不变，Pi 会自动把这些文件拼进 system prompt。

**动态内容走 `context` 事件。** 待复习卡片数、学习进度这类每轮可能变化的状态，在每次 LLM 调用前注入（见 `docs/pi-hook机制调研.md`）。这条路径的关键性质是：不写入 jsonl、不受自动压缩影响、每轮重新计算。

分开的理由是成本与正确性：静态内容每轮重注入是浪费，动态内容写进文件则会立刻过期。

## Consequences

- 新增一种学习模式通常只需在 `agents_md` 表里加一行提示词，不需要新的代码路径。模式因此是可扩展的，且可在 WebUI 里增删改。
- 上下文组装器承担了系统绝大部分的可配置性，值得单独设计并测试。它是「同一份业务状态如何呈现给模型」的唯一出口。
- 任何试图用提示词表达硬约束的做法都应被拒绝——模型会违反，而违反的代价是脏数据。
- 反之，任何试图用 schema 字段表达行为倾向的做法也应被拒绝——它会让代码里多出一个分支，而提示词里还要把这个分支的含义再写一遍，两处都得维护。
