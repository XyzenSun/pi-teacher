# 模式差异由提示词注入表达，硬约束由代码强制

学习空间之间的差异、制卡倾向的三档、学习会话与复习会话的不同——这些区分**几乎都不是代码分支，而是注入给模型的内容差异**。系统不为每种模式写一套独立逻辑，而是用同一套流程配上不同的注入内容。

因此**上下文组装器是核心模块**：它根据会话类型、所属学习空间的配置、以及当前业务状态（待复习卡数、待确认提议、用户偏好），组装出这一轮的 system prompt 与 briefing。

## 但两类差异必须分开处理

**行为倾向 → 提示词。** 模型可以自行权衡、偶尔偏离也不造成数据损坏的：

- 「默认」与「激进」制卡的判据松紧
- 复习会话中制卡要克制，只在暴露新问题或引伸新知识时才做
- 教学风格、评分 rubric、追问深度
- 复习时按主题分组组织，不把不同领域混着问

**硬约束 → 代码。** 一旦被违反就产生错误数据或破坏不变量的：

- 「禁止制卡」——工具层直接拒绝，不能只写在提示词里
- 卡片去重——工具层比对后拒绝
- 提议必须确认才入库——状态机保证
- 到期队列的计算——FSRS 与查询决定，不由模型挑选
- 制卡前必须读取现有 Topic 列表——作为工具的输入要求，而非请求模型「记得先看一眼」

判断准则：**如果模型在某次调用中忽略了这条规则，后果是「这次表现不够好」还是「数据错了」？** 前者归提示词，后者归代码。

## Consequences

- 新增一种学习模式通常只需新增提示词片段，不需要新的代码路径。模式因此是可扩展的。
- 上下文组装器承担了系统绝大部分的可配置性，值得单独设计并测试。它是「同一份业务状态如何呈现给模型」的唯一出口。
- 反过来，任何试图用提示词表达硬约束的做法都应被拒绝——模型会违反，而违反的代价是脏数据。
