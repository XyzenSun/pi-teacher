# 维护提醒按轮次直接追加在用户消息后：判断在程序，内容由模型决定

- 状态：已采纳
- 日期：2026-09-10
- 相关：ADR-0005（模型只能提议，周期提醒只是「考虑是否需要维护」）、ADR-0006（按轮次注入提醒的载体）、ADR-0020（术语进库、只写引导）、ADR-0033（提示词四层来源与 `pi-session-user.md`）、ADR-0035（助教不维护全局偏好）
- supersedes：ADR-0006 中「按轮次注入提醒——写成 Pi Extension 或利用 hook 机制」这一句的载体选择；`CONTEXT.md` 里 Reminder 只提「维护卡片」的旧定义

> 状态补充（2026-09-11）：文案种类由 ADR-0039 扩展为「三段基础 + 学习精华追加段」。新增 `learningEssence`（键 `reminder_text_learning_essence`），仅学习会话命中时在基础文案后同轮追加，制卡开 / 关都适用；共用原间隔，不新增计数器。原三段基础文案及用户自定义内容不变。

## 背景

ADR-0005 定下「周期性提醒让模型考虑是否需要维护」，但 MVP 只做了状态注入：`context` 钩子每轮以 `<pi-teacher-context>` 自定义消息告诉模型当前活动、到期卡数、制卡开关；`appendSystemPrompt` 固定段只在会话开始时说一次 `pi-session-user.md` 的读写规则。全局 `USER.md`、会话级偏好、制卡这几件事「谁在什么时候想起来做」没有任何机制，全靠模型在长对话里自觉。真实使用里对话动辄几十轮，模型早把开头那句引导忘了。

第一版设计走了 `before_agent_start` 钩子、异步自定义消息、按类型的多套模板，被用户判定「设置的复杂了」。提醒的本质是一句话：「聊了这么多轮，想想要不要更新点什么」。它不需要独立的消息通道，也不需要程序去猜模型该维护什么。

## 决策

1. **判断在程序**：`POST /api/conversations/:id/command` 组装 prompt 时计算当前轮次 `turn = 本会话历史里 user 消息数 + 1`（从 SDK 会话条目现数，不另存计数器），`turn % N === 0` 即命中。`N` 是业务运行设置 `reminder_interval_turns`，默认 30，`0` 表示关闭。
2. **直接拼在用户消息末尾**，不走自定义消息、不走钩子、不异步。提醒随用户消息一起落 JSONL，历史里**保持可见**（用户定稿：前端不折叠、不隐藏），压缩后随摘要一起消失也无妨——它本来就是一次性的提示。
3. **内容由模型决定**：提醒只说「可以考虑」，是否更新、更新什么、要不要在回复里提到，都由模型判断（ADR-0005）。三种文案按会话类型与制卡开关选取：
   - 学习 / 复习 且制卡开：`<system-reminder>已与用户对话多轮，可以考虑更新用户偏好、用户信息与制卡。如果当前会话下用户针对本次会话提出了要求，而不是全局性要求你以后在其他任务也这么做，更新到 pi-session-user.md。此消息为系统提醒，如果你认为不需要维护，在回复用户时无需提及本消息</system-reminder>`
   - 学习 / 复习 且制卡关：同上去掉「与制卡」
   - 助教：`<system-reminder>已与用户对话多轮，可以考虑更新用户对你的要求，更新到 pi-session-user.md。此消息为系统提醒，如果你认为不需要维护，在回复用户时无需提及本消息</system-reminder>`——助教不维护全局用户偏好与用户信息（ADR-0035）
4. **文案是设置项**（2026-09-11 修订，取代最初的「模板文件放 `docs/` 由程序运行时读取」）：三段文案与 `N` 一样存 `setting` 表，键 `reminder_text_make_card_on` / `reminder_text_make_card_off` / `reminder_text_ta`，值是整段内容（含 `<system-reminder>` 标签）；缺行或空串即取 `server/src/prompts/defaults.ts` 的出厂文案 `REMINDER_TEXT_DEFAULTS`，写入空串等于删行恢复默认。每次发送现读，改完下一轮命中即生效。出厂文案与其他初始化提示词一起收在 `defaults.ts`，镜像不再带 `docs/`。
5. **`N` 存新表 `setting(key TEXT PRIMARY KEY, value TEXT NOT NULL)`**：这是 pi-teacher 自己的业务运行设置，与 Pi 的 `settings.json` 无关；缺行即默认值，不需要 seed。`GET/PATCH /api/config/settings` 扩 `reminderIntervalTurns` 与 `reminderTexts` 两个字段，「高级配置」Tab 加间隔输入框与三个文案编辑框（各带「恢复默认」）。

## 为什么不是别的

- **`before_agent_start` / `context` 钩子注入自定义消息**：多一条消息通道、多一份「显示还是不显示」「落不落 JSONL」的规则；用户判定过度设计。命中条件只依赖历史条数与数据库两个已知量，在路由层拼字符串就够了。否决。
- **由程序判断该维护什么（比对 USER.md、扫描制卡记录）**：程序不懂对话内容，判断只会错；ADR-0005 已把「是否维护」交给模型。否决。
- **前端渲染时隐藏 `<system-reminder>` 块**：用户明确要求保持可见——看得见才知道系统在做什么，也方便调词。否决。
- **`N` 写死常量**：不同用户的对话密度差别很大，30 轮对一个人是半小时、对另一个人是一周；做成设置项成本只是一张两列表。否决。
- **文案做成 `docs/` 下的模板文件由程序读取**（最初的第 4 条）：镜像得为此带上一截 `docs/`，宿主直跑与容器两套路径；而调词本来就是用户运行时的事，与 `N` 同表同接口最顺手。已改为设置项，出厂文案进代码。
- **复用 Pi `settings.json` 存 `N`**：那是 Pi 的文件，字段由 SDK 的 `SettingsManager` 定义，塞业务字段进去等于依赖它对未知键的容忍度。否决。

## 后果

- 命中的那轮用户消息末尾多一段固定文本，真模型可能在回答里复述标签（`docs/spec.md` 已记录此现象）；验证脚本断言只看 payload 里**最后一条** user 消息，不看历史。
- 轮次从会话历史现数：助教清除上下文（ADR-0035）后计数归零；`compact` 不影响计数（JSONL 条目不减少）。
- `steer` / `follow_up` 也是 user 消息，同样计入轮次、同样可能命中；不为它们做例外。
- 业务表增加 `setting`，`verify:schema` 与 `smoke` 的表清单同步。
- `CONTEXT.md` 的 Reminder 定义改为「按轮次直接附在用户消息后的系统提醒，让模型考虑是否维护偏好、用户信息与卡片；可见、落历史」。
