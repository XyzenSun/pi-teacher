# Session、Pi Session、Card 的职责边界

> 状态：部分被 ADR-0030 取代——本文中「Session 拥有工作目录」的约定已改为 Pi Session 独占工作目录、Space 只是收纳容器。
>
> 2026-09-11 补充：`source_essence_path` 外部引用约定被 ADR-0039 取代，卡片不再保存精华路径；旧库幂等删列，精华文件保留为独立学习产出。其余职责边界论述仍有效。

这三者是系统的骨架，相互正交、各有独立生命周期。任何一个吞并另一个都会导致数据被错误地绑死，因此明确划分。

## 各自的职责

**Session（学习工作区）回答「我在推进哪件事」。** 它是一件具体的学习任务，对应一个目录，持有使命、术语表、学习记录、精华文档和历次对话。它是**上下文隔离单元**：学 Java 时不该被上周的数学笔记污染上下文。它是长期容器，会在数周至数月间累积几十次对话。其数量由用户同时推进的任务数决定，通常 1–5 个。

**Pi Session（对话）回答「这一场对话在做什么」。** 它是 Pi 管理的一整场多轮对话，一个 jsonl 文件，是**对话上下文单元**。

**Card（卡片）回答「哪块知识需要长期保持」。** 它归属 Topic，不归属产出它的工作区。它是**复习调度单元**。

## 生命周期是递增的

```
Pi Session（一次对话）  <  Session（一件学习任务，跨周跨月）  <  Card / Topic（跨年）
```

## 卡片为何不挂在工作区下

尽管工作区是长期容器，卡片仍不能挂在它下面，理由有两条，第二条更强：

1. **卡片的存活期超出工作区的活跃期。** 面试考完后，那个工作区不再有新对话，但它产出的卡片仍需继续复习数月甚至数年。
2. **多个工作区会喂给同一个 Topic。** 「准备后端面试」和「读《算法导论》」两个工作区都会产出 Java 相关的卡片。复习时它们必须汇到同一个队列里——按掌握程度调度，而不是按当初在哪个工作区学的。若卡片挂工作区，复习队列会按容器碎成几份，这是纯粹的损失。

卡片不存工作区外键，也不存来源对话的引用。要知道一张卡为何存在，读它的 `reason_and_remark`——模型在制卡时写下的原因与补充说明。这比一个指向长对话中某条消息的锚点更有用，也不需要解析 jsonl 去定位。

## 关系

- Session 一对多 Pi Session。外键在 Pi Session 上。
- Card 多对一 Topic。**Topic 由 AI 逐卡判定，不由对话预设**：一次对话可能前半段聊 JVM、后半段问一句英文表达，若在开场就把 topic 定死，后者会被永久归错类，复习时再也捞不出来。
- 复习对话可选一个 Topic 做过滤，不选即全部。
- **学习对话不携带 Topic，也不受 Topic 限制。** Topic 只是复习时精准捞卡的过滤器。
- Card 不持有任何指向 Session 或 Pi Session 的外键。唯一的外部引用是可空的 `source_essence_path`——卡片凝结自哪份精华文档，绝对路径，复习时可跳回看全貌。

## Space 是类型标记，不是容器

学习、复习、助教这三者是**对话的类型**，不是三种空间实体。它们决定一次对话用哪套提示词、能否制卡、是否按主题过滤卡片，仅此而已。

- 学习对话归属某个工作区，跑在该工作区目录下。
- 复习对话不归属任何工作区，跑在平铺的 `review/` 目录。它不是一件要推进的任务，而是一个反复执行的动作。
- 助教对话归属那个全局唯一的助教工作区。它可以按需被告知某个学习工作区的路径，从而查阅那边的上下文，但它本身不住在那里。

这消除了「复习空间」会带来的多态外键与可空字段互斥问题。

## Pi 与业务库的分工

Pi 持有对话的全部消息内容（见 ADR-0004，物理分离）。业务库的 pi_session 表只保存引用与展示元数据：所属工作区、jsonl 路径、标题、提示词模板、教学风格、时间。业务库不复制消息内容；需要原文时按路径回查 jsonl。

一张 pi_session 表同时容纳学习、复习、助教三类对话，用 `space_id` 判别。这样对话列表、标题编辑、历史查看只需实现一次。三者的差异只在几个字段的取值约束上。

## 提示词挂在pi对话上，不挂在工作区上

同一个工作区里，这次可以用「新学」提示词，下次用「新学不制卡」，再下次换个教学风格。选择发生在开对话的那一刻，之后对话期间不变。若挂在工作区上，就得为「这次想换个风格」而修改工作区配置，语义错位。

## Consequences

- 工作区不绑定 Topic。若绑定，工作区就退化为按领域划分的大杂烩，卡片也会重新被工作区的层级困住。
- 制卡前必须读取现有 Topic 列表并优先复用，无法匹配才提议新建。否则会长出「Java」「Java 后端」「JVM」这类近义主题，把复习队列切碎——这与卡片暴涨是同一类失控，只是发生在分类层。
- 卡片与产出它的对话之间没有数据库层面的连接。代价是无法做「列出这次对话产出的所有卡片」这类查询；换来的是不必为溯源维护外键，也不必承担 jsonl 消息定位的性能开销。
