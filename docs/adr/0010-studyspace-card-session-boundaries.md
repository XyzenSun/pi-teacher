# StudySpace、Card、Session 的职责边界

这三者是系统的骨架，它们相互正交、各有独立生命周期。任何一个吞并另一个都会导致数据被错误地绑死，因此明确划分。

## 各自的职责

**StudySpace 回答「我在推进哪件事」。** 它是一件具体的学习任务，持有学习目标、用户提供的资料、历次学习会话和学习产出，并负责组装 briefing。它是**上下文隔离单元**：学 Java 时不该被上周的数学笔记污染 briefing。它是长期容器，会在数周至数月间累积几十场会话。其数量由用户同时推进的任务数决定，通常 1–5 个。

**Card 回答「哪块知识需要长期保持」。** 它归属 Topic，不归属产出它的空间。它是**复习调度单元**。

**Session 回答「这一场对话在做什么」。** 它是 Pi 管理的一整场多轮对话，是**对话上下文单元**。

## 生命周期是递增的

```
Session（一场对话）  <  StudySpace（一件学习任务，跨周跨月）  <  Card / Topic（跨年）
```

StudySpace 是长期容器，会在数周至数月间累积几十场会话。Session 归属于它。

## 卡片为何不挂在空间下

尽管空间是长期容器，卡片仍不能挂在它下面，理由有两条，第二条更强：

1. **卡片的存活期超出空间的活跃期。** 面试考完后，那个空间不再有新会话，但它产出的卡片仍需继续复习数月甚至数年。
2. **多个空间会喂给同一个 Topic。** 「准备后端面试」和「读《算法导论》」两个空间都会产出 Java 相关的卡片。复习时它们必须汇到同一个队列里——按掌握程度调度，而不是按当初在哪个空间学的。若卡片挂空间，复习队列会按容器碎成几份，这是纯粹的损失。

空间只作为「产地」记录在卡片的溯源字段里。

## 关系

- StudySpace 一对多 Session（学习会话）。外键在 Session 上。
- Session 一对多 Card（该会话产出的卡片，用于溯源）。
- Card 多对一 Topic。**Topic 由 AI 逐卡判定，不由会话预设**：一场对话可能前半段聊 JVM、后半段问一句英文表达，若在开场就把 topic 定死，后者会被永久归错类，复习时再也捞不出来。
- Session（复习会话）多对多 Topic。复习时可选任意若干 Topic，不选即全部。
- **学习会话不携带 Topic，也不受 Topic 限制。** Topic 只是复习时精准捞卡的过滤器。

## Pi 与业务库的分工

Pi 持有会话的全部消息内容（见 ADR-0004，物理分离）。业务库的 Session 表只保存引用与展示元数据：所属空间、Pi 会话标识、标题、时间。业务库不复制消息内容；需要原文时按标识回查 Pi。

一张 session 表同时容纳学习会话与复习会话，用 `kind` 判别。这样会话列表、标题编辑、历史查看只需实现一次。二者的差异是：学习会话持有空间外键，复习会话不持有。

## Consequences

- 「复习」不是一个学习空间。它不是一件要推进的任务，而是一个反复执行的动作，因此建模为功能入口而非空间。这消除了「复习空间」带来的多态外键或可空字段互斥问题。
- 空间不绑定 Topic。若绑定，空间就退化为按领域划分的大杂烩，而卡片也会重新被空间的层级困住。
- 制卡前必须读取现有 Topic 列表并优先复用，无法匹配才提议新建。否则会长出「Java」「Java 后端」「JVM」这类近义主题，把复习队列切碎——这与卡片暴涨是同一类失控，只是发生在分类层。
