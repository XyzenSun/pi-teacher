# 扩展能力按职责选择载体，不统一插件化

> 状态：被 ADR-0027 收口——「skill 还是 MCP，接入时再定」的口子已关闭，MCP 不引入；载体按职责选择的原则仍有效。

项目需要多种可扩展能力（教学风格、周期提醒、业务写入、外部服务），但不把它们粗暴归为同一种「插件」。

载体的选择依据**不是「能不能执行代码」**——Skill 本身就可以携带脚本或可执行文件，由模型按需调用。真正的依据是**谁来保证这次调用的权限、成本与可审计性**：

- 模型自己决定是否使用、失败了也无所谓的能力——用 Skill。制卡规范、评分 rubric 是典型；附带脚本的 Skill 同样属于这一类。
- 需要介入 Agent Loop、按轮次注入提醒、监听会话生命周期——写成 Pi Extension 或利用hook机制 
- 必须由业务侧强制约束权限、成本、参数校验和审计的操作——用结构化 tool 调用到应用服务，不能交给模型自行发挥。卡片入库、偏好写入、调度状态变更都属于这一类。
- 数据库访问、调度计算、空间服务、到期队列等确定性逻辑——就是普通应用模块。
- 跨 Agent 底座复用的外部能力——用 MCP。远程代码沙箱是首选候选。（**修订**：MCP 已否决，见 ADR-0027；外部能力统一走插件封装，沙箱亦然。）
- **用户需要在界面上自定义、增删改的模型行为——用数据库表存 prompt 片段，由上下文组装器注入。** 教学风格是典型：它不是开发者预置的行为规范，而是用户随时会加一种、改一种的东西，放进 Skill 文件会让用户去改文件系统。

Skill 与「数据库存 prompt」的分界：**谁维护它。** 开发者维护的归 Skill，用户维护的归数据库。

## Consequences

- 只有一个实现的东西不提前抽成动态接口，避免为「可扩展」制造复杂度。
- Pi Extension 在 Node 进程内运行、权限高且无内置沙箱，因此只加载受信任的扩展。
- 同一个能力可能随需求变化更换载体，选择载体时按当前需要决定，不预先固化。
