# 学习区设计对数据库的影响

对照 `docs/学习区设计.md`，核对 `数据库设计.md` 需要怎么调整。

## 数据库的职责边界

**数据库只做两件事：给前端提供渲染所需的读取性能，以及卡片管理。**

模型读写的散文（MISSION.md、GLOSSARY.md、USER.md、learning-records）不进库。但**提示词类文件进库**——AGENTS.md、style.md 需要在 WebUI 里编辑，属于前端要读写的东西。文件是数据库的投影，不是源。

## 核心变化：session 的定位翻转了

设计文档第一句：「session 相当于学习工作区」。

原 schema 里 session 是**一次对话**。新设计里 session 是**工作区本身**——`learn/5/` 这个目录就是 session 5，装着 MISSION.md、GLOSSARY.md、`learning-records/`、`essence/`，以及若干 `*.jsonl`。

`learning-records/` 存在的理由就是上下文会丢，说明它天然跨对话。所以拆两层：

- **session** = 学习工作区，长生命周期，1 个目录，N 次对话
- **pi_session** = 一次 Pi 对话，1 个 jsonl 文件

## session（改）

```sql
CREATE TABLE session (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  name           TEXT NOT NULL,
  work_path      TEXT NOT NULL,
  teach_style_id INTEGER REFERENCES teach_style(id),
  agents_md      TEXT NOT NULL,
  created_at     TEXT NOT NULL DEFAULT (datetime('now'))
);
```

| 字段 | 说明 |
| --- | --- |
| `id` | 0 号是全局唯一的助教工作区（`~/pi-teacher/ta`），`name` 填「助教」。AUTOINCREMENT 从 1 开始，初始化时显式插入 id=0 这行。 |
| `name` | **用户自定义的自由文本**，创建工作区时手写。不是学习目标，也不由 AI 生成，AI 无权修改。后期可在 WebUI 改。 |
| `work_path` | `~/pi-teacher/learn/5`。能由 id 推导，但根目录在 Docker 与本地部署下不同，显式存更稳。 |
| `teach_style_id` | 教学风格外键，投影成 `style.md`。 |
| `agents_md` | 本工作区 AGENTS.md 的正文，WebUI 可编辑，投影成 `AGENTS.md`。 |

不加 `custom_instruction`：用户对工作区的特殊要求写进 `learn/5/USER.md`，模型直接读，前端不渲染。

## AGENTS.md 与 style.md 都是数据库的投影

两个文件都存库、都在新开对话时整份覆盖写出。

```
learn/5/
  ├─ AGENTS.md      ← 程序生成，内容 = session.agents_md
  ├─ style.md       ← 程序生成，内容 = teach_style.prompt
  ├─ USER.md        ← 用户自己写，不进库
  ├─ MISSION.md
  ├─ GLOSSARY.md
  ├─ essence/
  ├─ learning-records/
  ├─ assets/
  └─ *.jsonl
```

写入时机：**新开 pi_session 时**，两个文件都整份覆盖。

```
新开对话
  → 读 session.agents_md   → writeFile('learn/5/AGENTS.md', ...)
  → 读 teach_style.prompt  → writeFile('learn/5/style.md', ...)
  → SessionManager.create(...)
```

WebUI 编辑走同一条路：改数据库，下次开对话时覆盖生效。

**用户手动改文件我们不管**——下次开对话会被覆盖，不做冲突检测，不做回读合并。数据库单向是源。

分成两个文件而不是把风格拼进 AGENTS.md：风格来自 `teach_style` 表可在多个工作区复用，AGENTS.md 是本工作区专属。两者生命周期不同，混在一个字段里改风格就得重新拼接全文。AGENTS.md 里写一段引导指向 `style.md` 和 `USER.md`。

## pi_session（新增）

```sql
CREATE TABLE pi_session (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id       INTEGER REFERENCES session(id),
  space_id         INTEGER NOT NULL REFERENCES space(id),
  name             TEXT,
  path             TEXT NOT NULL UNIQUE,
  enable_make_card INTEGER NOT NULL DEFAULT 1,
  review_topic_id  INTEGER REFERENCES topic(id),
  created_at       TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (space_id = 2 OR review_topic_id IS NULL),
  CHECK (space_id = 1 OR session_id IS NULL)
);
```

| 字段 | 说明 |
| --- | --- |
| `session_id` | 归属的学习工作区。复习对话为 `null`（跑在 `review/`），助教对话归 `session_id = 0`。 |
| `space_id` | 会话类型。 |
| `name` | 这次对话在干什么。**这是 AI 唯一有权命名的东西**，首轮结束后由后端独立 LLM 调用生成，用户也可改。 |
| `path` | jsonl 绝对路径。`SessionManager.create()` 返回后立即 `getSessionFile()` 取得，不需要回填。 |
| `enable_make_card` / `review_topic_id` | 从 session 搬来，语义不变。 |

一个工作区允许多个并发 pi_session。`learning-records/` 编号和 `GLOSSARY.md` 的并发写冲突**不处理**——概率低，后果轻（顶多一条记录覆盖或编号重复），加锁的复杂度不值得。

## card（只加一个字段，其余不动）

原有字段全部保留，`answer_mode` 也保留：

```sql
CREATE TABLE card (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  topic_id              INTEGER NOT NULL REFERENCES topic(id),
  front                 TEXT NOT NULL,
  back                  TEXT NOT NULL,
  answer_mode           TEXT NOT NULL DEFAULT 'open_ended',
  metadata              TEXT,
  source_pi_session_id  INTEGER REFERENCES pi_session(id),   -- 原 source_session_id，仅改名
  source_message_id     TEXT,
  source_essence_path   TEXT,                                -- 新增
  created_at            TEXT NOT NULL DEFAULT (datetime('now')),

  CHECK (answer_mode IN ('open_ended', 'exact', 'code'))
);
```

两处变动：

- `source_session_id` → `source_pi_session_id`：外键指向变了。溯源要精确到哪次对话，指工作区太粗（一个工作区几十次对话）。
- 新增 `source_essence_path`：卡片出自哪个 essence 文件，相对 `work_path`（如 `essence/docker-network.html`）。设计说 essence 是制卡资料来源、卡片是凝结的精华，这个字段让复习时能跳回精华文档看全貌。存路径不存外键，因为 essence 不建表；文件被删或改名则字段悬空，复习界面按「文件不存在就不显示跳转」处理。

## review_log（只有一处改名）

原表：

```sql
  session_id  INTEGER NOT NULL REFERENCES session(id),
```

改成：

```sql
  pi_session_id  INTEGER NOT NULL REFERENCES pi_session(id),
```

**就这一行，其他字段全不动。**

原因：这个字段的用途是「这次 `Again` 是在哪场会话里发生的」。原来 session 就是一次对话，指它没问题。现在 session 变成了工作区，指它就只能定位到「在 Docker 那个工作区里答错的」，而不是「在 3 月 5 号那次复习对话里答错的」——粒度丢了。所以外键跟着 card 一起改指 pi_session。

`rating`、`ai_evaluation`、before/after 那 8 个快照字段、`reviewed_at`，全部保持原样。

## space / topic / card_schedule / teach_style

不变。

## 不进数据库的东西

| 文件 | 理由 |
| --- | --- |
| `USER.md`（全局 + 工作区级） | 用户偏好与特殊要求，模型直接读，前端不渲染 |
| `MISSION.md` | 模型读写的散文，无结构化查询需求 |
| `GLOSSARY.md` | 同上 |
| `learning-records/NNNN-slug.md` | 顺序编号由文件系统提供 |
| `essence/*.html` | 用户直接看的成品，文件名即标题 |
| `materials/index.md` | 已定：普通 Markdown，模型自己读写 |
| `assets/` | 设计明确写了「无需索引」 |

## 助教的「知道当前学习上下文」

前端传 `session_id`，后端读该工作区的 `AGENTS.md`，连同 `work_path` 一起拼成 system-reminder 注入助教这一轮请求。不读 MISSION.md、GLOSSARY.md、learning-records——给了路径，助教需要时自己用文件工具读。助教仍在 `ta/` 目录运行。

## 目录布局同步

需要更新 `数据库设计.md` 的目录布局：

1. 新增全局 `USER.md`
2. `materials/origins/` 存原件（PDF 等），`materials/` 本体只放可读格式
3. 新增根级 `assets/`（跨工作区复用），工作区级 `learn/5/assets/`（不复用）
4. 工作区内新增 `MISSION.md`、`GLOSSARY.md`、`USER.md`、`style.md`、`essence/`、`learning-records/`
5. `ta/` 和 `review/` 只有 AGENTS.md + jsonl，不需要 MISSION/GLOSSARY

注：设计文档里 `assest` 应为 `assets`，`GLOSSARY.md` 那段重复出现了两次（第 20、22 行）。

## 待确认

`ta/` 和 `review/` 的 AGENTS.md 也存库吗？它们全局唯一，不属于任何学习工作区。助教有 `session_id = 0` 那行可以挂 `agents_md`，复习没有对应的 session 行。三个选择：给复习也建一行 session（id 用 -1 之类）、单独建一张 `global_prompt` 表、或者复习的 AGENTS.md 就手写不进库。倾向最后一个，等真需要在 WebUI 编辑复习提示词时再加。
